# CheckIt 백엔드 설계

사용자와의 질의응답을 바탕으로 작성하는 설계 초안입니다. 확정한 사항과 미정 사항을 구분하고, 답변에 따라 갱신합니다.

## 확정 사항

### 1. 계약서 입력 방식

- 첫 버전에서 PDF와 사진 업로드를 모두 지원합니다.
- 사용자는 두 입력 방식 중 하나를 선택해 계약서를 제출할 수 있습니다.
- 한 계약서는 PDF 한 파일 또는 사진 여러 장 중 한 방식으로만 제출합니다. PDF와 사진의 혼합 제출은 허용하지 않습니다.
- 프론트엔드의 입력 제한과 함께 백엔드에서도 혼합 제출을 검증해 거부해야 합니다.
- 지원 사진 형식은 JPG·JPEG, PNG, HEIC입니다. ‘모두 지원’은 이번에 제시한 형식에 대한 결정이며, 그 외 이미지 형식 지원은 확정하지 않았습니다.
- HEIC는 서버에서 읽을 수 있도록 디코딩·변환 처리를 설계합니다. 원본은 보존하고 OCR·미리보기용 파생 이미지의 페이지·영역 연결을 유지합니다. 구체적인 라이브러리·변환 방식은 추후 결정합니다.

### 2. 파일 선택과 사진 페이지 순서

- 사진은 기기의 앨범에서 여러 장을 선택해 하나의 계약서로 제출합니다. 예: 3페이지 계약서는 페이지별 사진 3장을 선택합니다.
- PDF는 노트북 또는 휴대폰의 파일 선택창에서 찾아 선택합니다.
- 사진 선택 후 사용자가 페이지 순서를 확인하고 변경할 수 있습니다.
- 분석에는 사용자가 최종 확정한 페이지 순서를 사용합니다. 백엔드는 이 순서를 보존해야 합니다.

### 3. 분석 시작과 사진 편집

- 파일 선택만으로 텍스트 추출이나 계약 내용 분석을 시작하지 않습니다.
- 사용자가 ‘텍스트 추출하기’ 버튼을 누르면 확정한 파일 목록과 페이지 순서로 텍스트를 추출합니다.
- ‘텍스트 추출하기’를 누르기 전까지 사진 추가, 삭제, 페이지 순서 변경을 지원합니다.
- 텍스트 확인·수정 후 ‘확인 후 분석 시작’을 눌러 계약 내용 분석을 진행합니다.
- 파일을 서버로 전송하는 시점과 임시 파일 관리 방식은 아직 결정하지 않았습니다.

### 4. 분석 전 텍스트 확인

- 전체 텍스트 확인을 기본으로 강제하지 않고, 임금·근로시간·계약기간 등 핵심 항목과 인식이 불확실한 부분을 우선 표시합니다.
- 핵심 정보는 OCR 신뢰도와 관계없이 우선 표시합니다. 구체적인 항목 목록과 검토 대상 선정 기준은 추후 정의합니다.
- 항목을 선택하면 계약서 원본의 해당 영역과 추출 문장을 비교하고 수정할 수 있도록 합니다.
- 전체 텍스트도 선택적으로 확인·수정할 수 있도록 합니다.
- 읽을 수 없는 페이지는 임의로 내용을 채우지 않고 재업로드를 안내합니다.
- OCR 신뢰도만으로 정확성을 보장하지 않으며, 누락·미인식 항목을 정상 값으로 취급하지 않습니다.
- 계약 내용 분석은 사용자가 확인·수정한 텍스트를 기준으로 수행합니다.

### 5. 확정된 기본 흐름

계약서 종류 직접 선택 → 파일 선택 → 사진 추가·삭제·순서 편집 → ‘텍스트 추출하기’ → 핵심 정보·확인 필요 부분 검토 및 수정 → ‘확인 후 분석 시작’ → 분석 결과

### 6. 분석 결과의 기본 구성

- 전체 요약, 조항별 검토(계약 문장·설명·근거 법령), 누락·추가 확인 사항을 기본 구성으로 합니다.
- 사용자가 첨부한 리포트 이미지는 참고 시안이며, 화면의 세부 기능과 문구는 확정 사항이 아닙니다.

### 7. 첫 버전 분석 결과 기능 범위

다음 6개 기능을 첫 버전 범위로 확정합니다. 기능 범위의 확정이며, 세부 판정 기준·상태 명칭·지원 점검 항목은 별도로 결정합니다.

| 기능 | 범위 |
| --- | --- |
| 전체 요약 | 우선 확인할 사항과 점검 상태별 건수 |
| 점검 항목 목록 | 위약금·임금·근로시간 등 주제별 표시. 구체적인 지원 항목 목록은 미정 |
| 상세 설명 | 계약 문장과 주의할 이유를 쉬운 말로 안내 |
| 근거 법령 | 조문 원문·번호·시행일·공식 출처 링크 |
| 누락·추가 확인 | 찾지 못한 내용과 판단에 필요한 정보 표시 |
| 원본 연결 | 선택 항목의 해당 페이지 이동 및 영역 강조 |

- ‘이렇게 물어보세요’ 질문 예시, PDF 리포트 내보내기, 공유 링크, 개인정보 자동 마스킹, 자유형 후속 질의응답은 이번에 확정한 첫 버전 결과 기능 범위에 포함하지 않습니다.

### 8. 지원 계약서 범위

- 근로계약서는 아르바이트·단시간·정규직·계약직을 모두 지원 대상으로 합니다.
- 서비스 전체를 근로계약서에만 한정하지 않고 다른 계약서 유형도 고려합니다.
- 추가 계약서의 종류와 첫 버전 포함 여부는 아직 확정하지 않았습니다.
- 지원 대상의 확정은 해당 유형의 모든 조항에 대한 자동 판정이 구현되었다는 의미가 아닙니다. 유형별 점검 항목·적용 조건·법령 데이터 범위는 별도로 설계합니다.

### 9. 조항 분류 데이터 수집·서비스 연계 계획

- 사용자가 제공한 계획은 근로(고용)·아르바이트·연봉계약서를 핵심으로, 기타고용·인사노무 문서에서 선별한 조항을 학습에 추가하는 구성입니다.
- 조항은 임금, 근로시간, 휴일, 휴가, 근무 장소·업무, 계약기간, 계약 종료, 손해배상·위약금, 기타 근로조건, 그 외의 10개 주제로 다중 라벨 분류하는 계획입니다.
- 분류 결과를 점검 항목 구성과 관련 법령 검색에 연결합니다. 분류 라벨만으로 누락·위법 여부를 판정하지 않고 세부 정보 추출·적용 조건 확인을 별도로 설계합니다.
- 학습에 사용하는 기타 문서 종류를 서비스 지원 계약서 유형으로 자동 확장하지 않습니다.
- 수집·전처리·분할·학습·평가 및 확인 사항은 [조항 분류 데이터·서비스 연계 계획](clause-classification-data-plan.md)에 기록합니다. 제공 자료 기준이며 실제 데이터·모델 구현 완료를 확인한 것은 아닙니다.

### 10. 학습·평가 데이터 분할 방식

- 원래 제공된 TL/VL 구분을 유지합니다. 근로 관련 TL은 학습 90%·검증 10%, 근로 관련 VL은 최종 평가에 사용합니다.
- 양식 그룹으로 전체를 다시 나누는 방식은 채택하지 않습니다. 이전 그룹 분할안의 문장 수와 라벨별 통계는 참고 이력이며 새 기준으로 재집계해야 합니다.

### 11. 비회원 이용과 로그인 시 기록 저장

- 비회원도 계약서 업로드·텍스트 확인·분석·결과 조회를 이용할 수 있습니다.
- 로그인한 상태에서 분석하면 완료된 분석 결과와 계약서 원본을 해당 계정에 자동 저장합니다. 별도의 ‘기록 저장’ 버튼을 누를 필요가 없습니다.
- 카카오·구글 소셜 로그인과 이메일·비밀번호 로그인을 지원합니다. 계정에 저장된 기록의 보관 기간은 아래 보관 정책을 따릅니다.
- 비회원 결과 화면에 ‘로그인하고 기록 저장’을 제공합니다. 해당 버튼을 통해 로그인을 완료하면 방금 분석한 결과를 계정에 저장합니다. 재업로드·재분석은 요구하지 않습니다.
- 로그인 중에도 저장 대상 결과를 유지하고, 로그인 완료 후 해당 비회원 결과의 접근 권한을 확인한 다음 계정에 연결해야 합니다. 구체적인 임시 접근 확인 수단과 중복 저장 방지 방식은 추후 설계합니다.
- 계정에 저장하지 않은 비회원의 계약서 원본·추출 및 수정 텍스트·중간 산출물·분석 결과·작업 정보는 해당 계약서의 첫 파일 업로드 시점부터 24시간 임시 보관 후 자동 삭제합니다. 진행 중·미완료·완료·실패·취소 작업에 공통 적용합니다. 이전의 분석 완료 시점 기준은 적용하지 않습니다.
- 같은 계약서에 사진을 추가하거나 텍스트를 수정·분석·재분석·취소해도 보관 기한을 연장하지 않습니다. 계약서별 첫 업로드 시각과 만료 시각을 서버에서 관리합니다. 업로드 시작·수신 완료 중 정확한 서버 이벤트 기준은 기술 설계 시 정의합니다.
- 24시간 이내에 ‘로그인하고 기록 저장’을 완료한 기록은 계정 기록 보관 정책으로 전환해, 비회원 임시 보관 만료로 삭제하지 않습니다.
- 비회원은 같은 기기·브라우저에서 다시 접속해 진행 상태와 완료 결과를 확인할 수 있습니다. 재접근은 비회원 데이터의 공통 24시간 보관 기한 내에 가능합니다.
- 비회원 접근 확인 수단과 만료 데이터의 기술적 정리 방식은 미정입니다.
- 구현 시 회원의 분석 기록은 해당 사용자에게만 접근을 허용하고, 비회원 결과의 접근 확인 방식도 설계해야 합니다.

### 12. 계정에 저장하는 기록의 범위

- 계정에 기록을 저장할 때 분석 결과와 업로드한 계약서 원본(PDF 또는 사진)을 함께 저장합니다.
- 저장한 기록에서도 계약서 원본과 해당 부분을 연결해 확인할 수 있어야 합니다. 사진의 최종 페이지 순서와 분석 항목의 원본 연결 정보도 유지합니다.
- 회원 상태에서 수행한 분석과 비회원 분석 후 ‘로그인하고 기록 저장’으로 저장한 기록 모두에 적용합니다.
- 계정에 저장한 분석 결과와 계약서 원본은 사용자가 직접 삭제할 때까지 보관합니다. 일정 기간 경과에 따른 자동 삭제는 적용하지 않습니다.
- 이 보관 정책은 계정에 저장된 기록에 적용합니다. 계정에 저장하지 않은 비회원 데이터는 상태와 관계없이 공통 24시간 보관 후 자동 삭제 정책을 따릅니다.
- 사용자가 기록 삭제를 요청하면 삭제 확인을 표시하고, 확인 후 해당 분석 결과·계약서 원본·해당 기록에 종속된 원본 연결 데이터를 함께 삭제합니다.
- 휴지통과 사용자 복구 기능은 제공하지 않습니다. 삭제 확인 시 복구할 수 없다는 점을 안내합니다.
- 삭제된 기록은 이후 목록·상세·원본 조회에서 접근할 수 없어야 합니다. 실제 파일 삭제 실패의 재처리 및 백업에 대한 삭제 반영 방식은 기술 설계 시 정합니다.
- 회원 탈퇴 기능은 후속 요청으로 첫 버전에서 제외합니다. 개별 기록 삭제 기능은 유지합니다.

### 13. 이메일 회원가입 인증

- 이메일·비밀번호 회원가입 시 입력한 이메일 주소로 인증 링크를 발송합니다.
- 사용자가 링크를 통해 이메일 인증을 완료하면 가입을 확정합니다. 인증 전에는 가입 완료 상태로 취급하지 않습니다.
- 인증 대기 상태의 저장 방식, 링크 유효 시간·재발송·만료 처리, 인증 후 로그인 여부는 추후 결정합니다.
- 비회원 결과 저장을 위해 이메일 회원가입을 진행하는 경우, 가입·로그인 완료 후 기존 결과를 연결해야 합니다. 인증만으로 계정 저장 완료로 취급하지 않으며, 비회원 결과의 24시간 보관 기한을 적용합니다.

### 14. 비밀번호 재설정 — 첫 버전 제외

- 사용자 후속 요청으로 비밀번호 재설정 기능·API·메일 발송을 첫 버전에서 제외합니다. 앞선 지원 결정을 대체합니다.
- 이메일 로그인 및 기존 이메일 가입 인증은 유지합니다. 서로 다른 로그인 방식의 계정 연결은 2026-10-26 후속 요청으로 제외합니다.

### 15. 로그인 방식별 독립 계정 — 2026-10-26 변경

- 이메일·카카오·구글 간 계정 연결은 제공하지 않습니다. 앞선 계정 연결 유지 결정을 대체합니다.
- 제공자별로 별도 user_id를 만들고, 같은 이메일이어도 회원·분석 기록은 공유하지 않습니다. 원래 로그인 방식으로 접속해야 해당 기록을 확인할 수 있습니다.
- 연결·병합·연결 해제·이를 위한 재인증은 첫 버전 범위에서 제외합니다. 기본 가입·이메일 인증·로그인·로그아웃은 유지합니다.
- 비회원의 ‘로그인하고 기록 저장’은 유지하며, 그때 로그인한 특정 계정에만 귀속합니다. 이는 서로 다른 회원 계정의 통합이 아닙니다.

### 16. 회원 탈퇴 — 첫 버전 제외

- 사용자 후속 요청으로 회원 탈퇴 기능과 API는 첫 버전에서 제외합니다. 앞선 탈퇴 시 전체 데이터 삭제 기능의 구현 결정을 대체합니다.
- 개별 계약서의 삭제 확인 후 즉시 삭제·복구 불가 정책과 비회원 데이터 24시간 만료 삭제는 유지합니다.

### 17. 분석 화면에서 완료까지 대기

- 화면을 닫은 뒤에도 분석을 계속하고 진행 상태를 다시 조회하는 기능은 첫 버전에서 제외합니다. 앞선 화면 이탈 후 분석 지속·진행 상태 재접근 결정을 대체합니다.
- 사용자는 분석 화면을 유지하며 완료를 기다립니다. 분석 요청의 응답으로 결과 또는 오류 이유·복구 행동을 반환하는 방식으로 단순화합니다.
- 별도 작업 상태 조회 API와 프론트엔드 폴링은 제공하지 않는 방향입니다. 이미 저장된 완료 결과·원본을 회원 기록 또는 비회원 보관 기한 내에 다시 조회하는 기능은 유지합니다.
- 분석 성공 후 회원 자동 저장, 비회원 첫 업로드 후 24시간 보관 정책은 유지합니다.
- 브라우저 연결 종료는 서버 실행의 즉시 중단을 보장하지 않습니다. 연결 종료·시간 초과 시 후속 처리 중단, 늦은 결과 저장 여부, 재시도 중복 방지의 구체적인 규칙은 후속 설계 대상입니다. 사용자에게 종료 후 완료·재개를 약속하지 않습니다.
- 서버의 API 처리 이벤트 루프를 무거운 동기 모델 계산으로 막지 않도록 실행 방식을 정합니다. HTTP 응답을 기다리는 것과 서버 내부 작업 실행 방식은 별개입니다.
- 기존 명시적인 ‘분석 취소’ 기능은 아직 철회하지 않았습니다. 화면 이탈과 명시적 취소는 구분하며 아래 정책을 따릅니다.
- 분석 완료는 웹서비스 안에서만 표시하며 완료 이메일·브라우저 푸시는 제공하지 않습니다.

### 18. 분석 취소

- 화면 종료 후 분석 지속 기능을 제외한 이후에도, 사용자 요청에 따라 명시적인 ‘분석 취소’ 버튼과 취소 API는 유지합니다.
- 회원과 비회원 모두 자신에게 접근 권한이 있는 진행 중 분석에 대해 ‘분석 취소’를 요청할 수 있습니다.
- 취소 확인을 거친 요청은 서버에 전달하고, 해당 작업의 후속 분석을 중단합니다. 화면 이탈만으로는 취소하지 않습니다.
- 취소 처리 중과 취소 완료 상태를 구분합니다. 이미 실행 중인 외부 요청 등 즉시 중단할 수 없는 단계의 결과는 취소 확정 후 최종 결과로 게시하거나 완료 기록으로 자동 저장하지 않도록 설계합니다.
- 취소한 작업은 취소 상태로 남기고 계약서 원본과 확정한 페이지 순서를 유지합니다. 사용자는 원본 재업로드 없이 다시 분석할 수 있습니다.
- 취소된 작업은 완료된 분석 결과로 표시하지 않습니다.
- 회원의 취소 작업은 계정의 기록 목록에서 다시 접근할 수 있도록 유지하며, 사용자가 삭제하거나 탈퇴하면 관련 삭제 정책을 따릅니다.
- 비회원 취소 작업의 파일도 공통 24시간 임시 보관 정책을 따릅니다. 취소 상태라는 이유로 무기한 보관하지 않습니다.
- 취소와 완료가 동시에 발생했을 때의 처리, 중간 산출물·사용자 확인 텍스트의 재사용 범위, 재분석 실행 방식은 추후 설계합니다.

### 19. 분석 오류와 복구 경로

- 실패 이유에 따라 다음 행동을 안내합니다. 모든 오류에 일괄적으로 재업로드를 요구하거나 같은 재시도 버튼을 표시하지 않습니다.
- 파일·문서 자체의 문제로 내용을 읽을 수 없으면 원인을 안내하고 원본을 다시 업로드하도록 합니다. 예: 손상된 파일, 지원하지 않는 형식, 읽을 수 없을 정도로 흐린 사진. 구체적인 지원 형식과 품질 기준은 미정입니다.
- 원본을 유지한 채 재시도할 수 있는 일시적인 처리 오류라면 ‘다시 분석’을 제공합니다. 예: 외부 처리 서비스 시간 초과·일시적 장애. 실패한 처리 단계와 사용자 확인 상태에 맞춰 필요한 단계를 재시도하며, 텍스트 확인 전 계약 내용 분석을 임의로 진행하지 않습니다.
- 실패만으로 원본에 문제가 있다고 단정하지 않습니다. OCR 서비스 장애 등 처리 시스템 문제와 실제 읽기 불가능한 파일을 구분합니다.
- 권한·로그인·보관 기한 만료 등은 해당 상태에 맞는 안내를 제공합니다. 만료되어 원본이 삭제된 경우에는 재업로드가 필요합니다.
- 적용 조건이나 법령 근거가 부족한 항목은 전체 분석의 기술적 실패와 구분해, 결과의 ‘추가 확인’으로 안내하는 방향입니다. 세부 판정 기준은 별도 설계합니다.
- 비회원 재시도·재업로드가 기존 계약서의 파일 교체에 해당하면 첫 업로드 시점의 24시간 기한을 연장하지 않습니다. 새로운 계약서 업로드와의 구체적인 구분은 기술 설계 시 정합니다.
- 서버에서 오류 코드·실패 단계·재시도 가능 여부·필요한 사용자 행동을 구분하고 화면은 이에 맞는 설명과 버튼을 표시하도록 설계합니다. 사용자에게 원시 오류 로그를 그대로 노출하지 않습니다.
- 문서·파일 문제로 재업로드가 필요한 경우, 일부 페이지만 문제가 있어도 해당 계약서 전체를 다시 업로드하도록 합니다. PDF는 전체 파일을, 사진은 계약서를 구성하는 전체 사진을 다시 선택합니다. 오류 복구용 페이지별 교체 기능은 제공하지 않습니다.
- 이 정책은 오류 후 재업로드에 적용하며, 최초 ‘텍스트 추출하기’ 전 사진 추가·삭제·순서 변경 기능은 유지합니다.
- 원인을 판별하지 못한 오류의 안내, 재시도 횟수·대기 시간과 정상 처리 단계 재사용 범위는 아직 미정입니다.

### 20. 웹서비스 이용 환경과 완료 상태 표시

- 노트북·휴대폰의 웹브라우저에서 사용하는 웹서비스를 전제로 설계합니다.
- 분석 진행 상태와 완료 여부는 웹서비스 안에서 표시합니다. 회원은 분석 기록에서, 비회원은 같은 기기·브라우저로 다시 접속해 보관 기한 내에 확인합니다.
- 첫 버전에서는 분석 완료 이메일과 브라우저 푸시 알림을 제공하지 않습니다. 회원가입 인증 이메일은 유지하며, 비밀번호 재설정은 후속 요청으로 첫 버전에서 제외합니다.
- 진행 상태 갱신을 위한 폴링·SSE 등 기술 방식과 서비스 내부 표시의 세부 UI는 추후 설계합니다.

### 21. 계약서 종류 선택

- 업로드 전에 사용자가 계약서 종류를 직접 선택합니다. 자동 분류로 종류 선택을 대신하지 않습니다.
- 백엔드는 선택한 계약서 종류를 해당 계약서에 저장하고, 종류에 맞는 처리·점검 설정을 선택하는 데 사용합니다.
- 선택 가능한 계약서 종류 목록은 아직 미정입니다. 학습 자료의 문서 종류를 그대로 선택 목록으로 사용하지 않습니다.
- 근로계약서의 세부 유형은 사용자가 별도로 선택하지 않습니다. 문서 내용에서 계약기간·근로시간 등 정보를 추출해 자동으로 파악합니다.
- 정규직·계약직·아르바이트 등을 반드시 하나의 상호 배타적인 분류로 강제하지 않습니다. 기간제 여부와 단시간 여부는 함께 해당할 수 있으므로 각각의 속성을 구분하는 방향으로 설계합니다.
- 문서만으로 세부 유형을 파악할 수 없거나 정보가 충돌하면 미확인 상태로 두며, 추정만으로 적용 조건을 확정하지 않습니다. 자동 파악에 사용할 모델·규칙과 판정 기준은 추후 설계합니다.
- 사용자가 선택한 종류와 업로드 문서의 내용이 맞지 않을 때의 처리와 종류 변경 흐름은 추후 결정합니다.

### 22. 추가 질문 없이 결과에서 정보 부족 안내

- 첫 버전에서는 분석 전에 사업장 규모 등 계약서 외 정보를 묻는 별도 질문 단계를 제공하지 않습니다. 기존의 추출 텍스트 확인·수정 단계는 유지합니다.
- 계약서와 사용자가 확인·수정한 텍스트를 바탕으로 분석하고, 적용 조건이나 근거가 부족한 항목은 단정하지 않습니다.
- ‘누락 의심’은 점검 대상 내용이 계약서에 없거나 빈칸인 것으로 보이는 경우에 사용합니다. 적용 조건·인식 실패를 확인하지 못했다면 필수 내용의 누락이라고 단정하지 않습니다.
- ‘추가 확인 필요’는 문장이 있어도 적용 조건 등 판단에 필요한 정보가 부족하거나 불확실한 경우에 사용합니다.
- 추가 확인 항목에는 판단을 완료하기 어려운 이유와 사용자가 별도로 확인할 정보를 표시합니다. 결과 조회를 위해 추가 답변을 요구하지 않습니다.
- 결과에서 추가 답변을 받아 재분석하는 기능은 첫 버전 확정 범위에 포함하지 않습니다. 구체적인 항목별 판정 기준·상태 우선순위는 추후 설계합니다.

### 23. 한 번의 분석에 제출하는 계약서 수

- 한 번의 분석에는 계약서 한 건만 제출합니다. 여러 계약서를 한 번에 분석하는 일괄 제출 기능은 제공하지 않습니다.
- 하나의 계약서가 여러 페이지인 경우, 페이지별 사진 여러 장을 하나의 계약서로 묶어 제출할 수 있습니다. 사진 수를 계약서 건수로 계산하지 않습니다.
- 서로 다른 계약서는 각각 별도의 분석으로 제출합니다. 사용자당 한 번에 한 건만 분석을 진행하며, 동시 분석은 허용하지 않습니다. 아래 동시 실행 정책을 따릅니다.
- PDF는 한 번의 제출에 한 파일만 선택할 수 있습니다. 여러 PDF를 업로드해 합치는 기능은 첫 버전에 제공하지 않습니다.
- 한 계약서는 최대 10페이지까지 제출합니다. PDF는 최대 10페이지인 한 파일, 사진은 페이지당 한 장씩 최대 10장으로 제한합니다.
- 제한을 초과하면 업로드·검증 단계에서 안내하고 분석을 시작하지 않습니다. 백엔드에서도 PDF의 실제 페이지 수와 사진 장수를 검증합니다.
- 파일 하나당 최대 20MB, 계약서 전체 파일 합계 최대 100MB로 제한합니다. PDF·사진 모두 파일별 제한을 적용하며, PDF는 한 파일만 허용하므로 최대 20MB입니다.
- 페이지·장수 제한과 파일별·전체 용량 제한을 모두 충족해야 제출할 수 있습니다. 초과하면 제한과 해당 파일을 안내하고 분석을 시작하지 않습니다. 백엔드에서도 검증합니다.
- MB의 바이트 환산 기준과, 한 파일에 여러 계약서가 포함된 경우의 안내 방식은 기술 설계 시 결정합니다.

### 24. 비밀번호로 잠긴 PDF

- 열기 비밀번호가 필요한 PDF는 첫 버전에서 직접 분석하지 않습니다. 사용자가 기기에서 잠금을 해제한 PDF 전체를 다시 업로드하도록 안내합니다.
- PDF 비밀번호를 입력받거나 서버에서 비밀번호를 이용해 잠금을 해제하는 기능은 제공하지 않습니다.
- 잠긴 PDF가 확인되면 분석을 시작하지 않고 ‘비밀번호로 보호된 PDF입니다. 기기에서 잠금을 해제한 파일을 다시 업로드해주세요.’라고 안내합니다.
- 같은 계약서의 재업로드에는 기존 파일·페이지 수·용량 제한을 적용합니다. 비회원 보관 기한도 기존 첫 업로드 시점 기준을 유지합니다.
- 열기 비밀번호와 인쇄·복사 등의 권한 제한을 구별하는 구체적인 PDF 검사 방식은 기술 설계 시 정합니다.

### 25. 사용자 텍스트 수정과 재분석

- 기존 결정대로 분석 전에는 핵심 정보와 인식이 불확실한 부분을 우선 확인·수정합니다. 전체 텍스트도 필요하면 열어 수정할 수 있습니다.
- 분석 결과를 본 뒤에도 사용자가 텍스트 수정 화면으로 돌아가 원하는 내용을 직접 수정하고 재분석할 수 있습니다. OCR 오류 자동 탐지를 전제로 하지 않습니다.
- 분석 후 수정은 원본 재업로드 없이 가능하며, 사용자가 수정한 텍스트를 확정하고 분석을 요청하면 새 분석을 수행합니다. 수정만으로 기존 결과를 최신 분석 결과처럼 변경하지 않습니다.
- 업로드한 계약서 원본과 OCR 추출본은 사용자 수정 텍스트와 구분합니다. 원본 파일 자체를 텍스트 수정으로 덮어쓰지 않습니다.
- 분석 실행마다 입력한 텍스트 버전을 연결해, 결과가 어느 수정본을 기준으로 생성됐는지 식별할 수 있어야 합니다. 사용자가 바꾼 내용은 원본과 동일하다고 표시하지 않습니다.
- 사용자 추가·삭제 등으로 정확한 원본 영역과 연결하기 어려운 문장은 기존 위치를 임의로 강조하지 않습니다. 수정 여부·페이지 단위 안내 등 구체적인 표시는 추후 설계합니다.
- 회원의 재분석 완료 결과는 자동 저장 정책을 따릅니다. 비회원은 같은 계약서의 첫 파일 업로드 후 24시간 기한을 유지하며, 수정·재분석으로 기한을 연장하지 않습니다.
- 재분석이 성공적으로 완료되면 같은 계약서 기록의 결과를 최신 결과로 교체합니다. 이전 분석 결과를 별도 기록으로 제공하거나 비교·복원하는 기능은 제공하지 않습니다.
- 수정 또는 재분석 요청만으로 기존 결과를 지우지 않습니다. 재분석 진행 중·실패·취소 시에는 기존 결과가 이전 입력 기준임을 구분해 유지하고, 성공 완료 시 교체합니다.
- 분석 입력 텍스트 버전과 실행 ID를 연결해 교체할 결과를 식별합니다. 내부 처리 이력의 보관 범위·정리 방식과 동시 재분석 시 결과 교체 규칙은 기술 설계 시 정합니다.

### 26. 분석 동시 실행 제한

- 첫 버전은 사용자당 한 번에 한 건의 분석만 진행합니다. 서비스 전체를 한 건으로 제한하는 것은 아닙니다.
- 기존 분석이 완료·실패하거나 취소 처리가 완료된 후 다음 분석을 시작할 수 있습니다. 재분석도 동일한 제한을 적용합니다.
- 화면을 나가도 진행 중 작업이 있으면 추가 분석을 시작할 수 없습니다. 진행 중 작업을 안내하고 해당 상태 화면으로 이동할 수 있도록 합니다.
- 로그인 사용자는 공통 사용자 ID 기준으로, 비회원은 같은 브라우저의 임시 사용자 식별 기준으로 제한하는 방향으로 설계합니다. 여러 탭의 중복 요청도 서버에서 검증해야 합니다. 비회원의 다른 기기·브라우저까지 동일인으로 식별하는 것은 확정 범위가 아닙니다.
- 여러 작업을 예약하는 대기열 기능은 사용자 기능으로 제공하지 않습니다. 서버 내부의 작업 대기·실행 구조는 별도로 설계합니다.
- 텍스트 추출 중에도 동일한 제한을 적용할지와 분석 대기 중 다른 계약서 파일 업로드를 허용할지는 아직 결정하지 않았습니다.

### 27. 백엔드 언어·프레임워크

- 백엔드는 Python·FastAPI로 구현합니다. 백엔드 코드와 설계 문서는 `CheckIt_BE`에서 관리합니다.
- 기존 Python RAG와 조항 분류 추론 코드를 연결하는 방향으로 설계합니다. 데이터 수집·학습 코드 전체를 백엔드에 복사하는 것을 전제로 하지 않습니다.
- 분석 작업자 분리 구조는 추천안이며, 구체적인 실행 구조·작업 큐·DB·파일 저장소·인증 도구·배포 환경은 후속 설계에서 결정합니다.

### 28. 레포 분리와 AI 패키지 연계

- 프론트엔드·백엔드·AI 코드를 각각의 레포에서 관리합니다. 현재 데이터 레포를 실제로 이전·변경한 것은 아닙니다.
- AI 레포에는 데이터 수집·전처리·학습·평가 코드와, 서비스에서 사용할 OCR·분류 추론·RAG 검색·설명 생성 코드를 구분해 둡니다.
- 서비스용 AI 기능을 설치 가능한 Python 패키지로 구성하고 백엔드 실행 환경에 설치합니다. 백엔드 측 분석 코드에서 해당 패키지의 함수를 불러와 실행합니다. `checkit_ai`는 예시 이름이며 실제 패키지 이름·레포 이름은 아직 미정입니다.
- 첫 버전은 별도 AI HTTP 서버 없이 백엔드 서버에서 AI 기능을 실행하는 방향입니다. 패키지 설치 방식은 코드 연결 방식이며, 분석을 FastAPI 요청 프로세스 안에서 동기 실행한다는 뜻은 아닙니다. 작업자 프로세스·작업 전달 방식은 별도로 설계합니다.
- 개발 중에는 로컬 AI 레포의 editable 설치를 사용할 수 있습니다. 운영에서는 검증된 버전·커밋의 패키지를 설치해 배포하고, AI 레포 변경을 운영 환경에 자동 반영하지 않습니다.
- 모델 학습과 법령 인덱스 구축은 사용자 분석 요청과 분리해 수행합니다. 모델 가중치·법령 인덱스·DB 연결 설정은 실행 환경에 별도로 준비해야 합니다.
- 모델 및 인덱스의 저장 위치·공급 방법, 패키지 배포·접근 방식, 함수 입출력·오류 형식은 후속 설계에서 결정합니다.
- 이 결정은 연계 방식의 확정이며, 이번 단계에서 패키지 생성·설치·서버 구동은 수행하지 않았습니다.

### 29. 원본 파일 저장소

- 첫 버전은 업로드한 계약서 PDF·사진 원본을 서버의 전용 폴더에 저장합니다. 외부 객체 저장소 도입은 후속 검토 사항입니다.
- 서비스 DB인 PostgreSQL에는 실제 파일 대신 내부 저장 키·경로, 소유자, 파일 형식·용량, 페이지 순서, 업로드·만료 시각 등을 기록합니다. 구체적인 테이블은 DB 설계 초안을 따릅니다.
- 원본 폴더는 공개 정적 파일 경로로 노출하지 않습니다. 백엔드가 회원 또는 비회원의 접근 권한과 보관 기한을 확인한 뒤 원본을 제공합니다.
- 사용자 파일명 대신 서버가 생성한 저장 키를 사용합니다. 실제 서버 경로를 사용자에게 그대로 노출하지 않습니다.
- 기존 계정 기록 삭제·탈퇴·비회원 24시간 만료 정책에 따라 서버의 원본 파일과 종속 파생 파일도 정리해야 합니다.
- 서버 재시작·배포 때 파일이 사라지지 않는 영속 저장 경로를 사용합니다. 구체적인 디렉터리·볼륨 구성, 용량 관리·백업·삭제 재처리는 기술 설계 시 정합니다.
- 이번 결정은 저장 방식의 확정이며, 실제 저장 폴더 생성·업로드 구현·서버 배포는 수행하지 않았습니다.

### 30. 초기 실행 환경

- 초기에는 로컬 컴퓨터에서 백엔드를 실행하며, 운영 배포 환경은 나중에 결정합니다.
- 로컬에서 서버 전용 폴더에 저장한다는 것은 백엔드가 실행되는 컴퓨터의 디스크 내 지정 폴더에 저장한다는 의미입니다. 접속한 사용자 기기마다 파일을 저장하는 방식이 아닙니다.
- 예를 들어 `CheckIt_BE/storage/uploads/`를 사용할 수 있으나 실제 경로는 아직 확정하지 않았습니다. 경로는 실행 환경 설정으로 지정하는 방향입니다.
- 원본·파생 파일과 사용자 데이터를 Git에 포함하지 않도록 구현 시 제외 규칙을 적용합니다. 이번 문서 수정에서 실제 저장 폴더 생성·서버 구동은 수행하지 않았습니다.
- 향후 원격 서버로 배포하면 해당 서버의 영속 디스크·볼륨에 저장합니다. 컨테이너를 사용한다면 임시 컨테이너 파일시스템과 영속 저장 공간을 구분해 구성해야 합니다.

### 31. 서비스 DB와 RAG 검색 저장소

- 서비스 DB는 PostgreSQL, RAG 법령 검색 저장소는 Chroma로 확정합니다.
- PostgreSQL은 회원·로그인 연결·계약서·텍스트·작업 상태·현재 분석 결과를 관리하며, Chroma는 법령 청크·임베딩·검색 메타데이터를 관리합니다.
- 원본 파일은 앞서 정한 로컬 서버 전용 폴더에 저장하고 PostgreSQL의 파일 정보와 연결합니다.
- 테이블·관계·비회원 계정 귀속·결과 교체·삭제 절차는 [DB 구조 초안](database-design.md)에 정리합니다. DB 조합은 확정 사항이고 세부 스키마는 검토용 초안입니다.
- 프론트엔드와 백엔드의 핵심 요청·응답은 [API 명세 초안](api-design.md)에 정리합니다. 경로·필드·오류 코드는 검토용 제안이며 아직 구현하지 않았습니다.
- [로그인 API 명세안](auth-api-design.md)과 [AI 함수 입출력 명세안](ai-interface-design.md)을 별도로 작성했습니다. 사용자 요청은 명세 구체화이며 코드 구현이 아닙니다. 세션·토큰 수명 등의 신규 기술 기본값은 제안으로 구분합니다.

### 32. 화면 동작 단위 API 통합

- 프론트엔드의 화면 한 동작에 필요한 여러 처리는 하나의 공개 API로 묶습니다. 백엔드 내부는 검증·저장·AI 호출·소유권 전환 등 함수로 나누며 내부 함수마다 HTTP API를 만들지 않습니다.
- ‘텍스트 추출하기’는 계약서 생성·파일 업로드·페이지 순서 저장·OCR을 통합하고, ‘확인 후 분석 시작’은 수정본 저장·입력 확정·분석·결과 저장을 통합합니다.
- 업로드 전 사진 추가·삭제·정렬은 브라우저에서 처리하고 최종 목록을 한 번에 전송합니다. 전체 재업로드·추출 재시도·기록 목록·상세·원본 열기·삭제는 각각의 화면 동작으로 구분합니다.
- ‘로그인하고 기록 저장’은 로그인 완료 처리 안에서 선택한 비회원 계약서의 소유권 전환까지 수행할 수 있도록 합니다. 로그인 성공과 기록 저장 실패는 구분해 반환합니다.
- 로그인 API는 제공자별 독립 계정을 인증합니다. 계정 연결·이를 위한 재인증 분기는 제거합니다. 소셜 콜백·이메일 확인 등 시점이 다른 통신은 유지합니다.
- 분석 취소는 기존 결정대로 유지합니다. 화면 종료 후 지속·별도 상태 조회는 제외하고, 저장된 결과는 계약서 상세에 포함합니다.
- 최신 명세 기준 고유 HTTP API는 계약서·분석 10개 + 로그인·계정 9개 = 19개입니다. 비밀번호 재설정 2개·탈퇴 1개를 제외했습니다. 계정 연결은 2026-10-26 제외했으며 기존 내부 분기만 제거하므로 HTTP 경로 수는 동일합니다. claim 중복은 한 번만 세고 provider 패턴은 한 경로로 셉니다. 실제 서버 코드 구현은 아직 수행하지 않았습니다.

## 분석 결과 세부 설계 제안 — 미확정

### 확정된 저장소 조합의 세부 구성 제안

- 사용자는 PostgreSQL 사용 경험이 있으며 PostgreSQL·Chroma 조합을 선택했습니다.
- PostgreSQL은 회원·로그인 수단 연결·계약서·페이지 정보·분석 작업 상태·현재 분석 결과·비회원 만료 시각을 관리하는 용도입니다.
- Chroma는 법령 청크·임베딩·검색 메타데이터를 보관하고 유사 법령 검색에 사용합니다. 사용자 계정·분석 기록의 기준 저장소와 역할을 구분합니다.
- 분석에 사용한 법령 원문·식별자·시행일·출처·corpus 버전은 결과와 함께 PostgreSQL에 인용 스냅샷으로 보존하는 방향을 제안합니다. 인덱스 갱신만으로 저장된 결과의 근거가 바뀌지 않도록 합니다.
- 원본 파일은 사용자 선택에 따라 서버 전용 폴더에 저장합니다. PostgreSQL에는 저장 키·소유자·페이지 순서 등을 기록합니다. 미리보기 등 파생 파일의 세부 저장 구조는 미정입니다.
- 회원·작업 등 관계와 검색할 핵심 필드는 테이블로 설계하고, 가변 분석 세부 내용에는 필요에 따라 JSONB를 사용하는 것을 제안합니다. 전체 결과를 무조건 하나의 JSON에 넣는 것으로 확정하지 않습니다.
- PostgreSQL과 파일 저장소·Chroma 사이의 변경은 단일 DB 트랜잭션으로 모두 원자 처리되지 않으므로, 삭제·실패 재처리 절차를 별도로 설계합니다.
- 저장소 조합은 확정됐으며 이 절의 구체적인 저장 구조는 제안입니다. 실제 DB 설치·연결은 수행하지 않았습니다.
- 참고: [PostgreSQL 트랜잭션](https://www.postgresql.org/docs/current/tutorial-transactions.html), [JSON 타입](https://www.postgresql.org/docs/current/datatype-json.html), [Chroma 문서](https://docs.trychroma.com/).

### 백엔드 프레임워크 비교 기록과 실행 구조 제안

- Python·FastAPI와 Java·Spring Boot를 비교했고, 사용자는 Python·FastAPI를 선택했습니다. 아래 비교는 선택 배경이며 분석 실행 구조는 추가 설계 대상입니다.
- 현재 저장소의 RAG는 Python이며 `sentence-transformers`, `chromadb`, `kiwipiepy` 등을 사용합니다. 첫 버전은 Python·FastAPI를 추천합니다. 기존 검색 코드와 앞으로의 조항 분류 추론 코드를 같은 언어로 연결해 초기 통합·배포 구성을 줄일 수 있다는 프로젝트별 판단입니다.
- FastAPI는 타입 기반 입력 검증과 자동 API 문서를 제공하지만 DB·마이그레이션·인증·작업 큐 도구는 별도로 선택·구성해야 합니다.
- Spring Boot는 Spring Security 등 인증·권한 및 서비스 운영 생태계가 강점입니다. 팀에 Java·Spring 경험이 많으면 유력한 대안입니다. Python 모델 코드를 그대로 연결하려면 별도 Python 작업자·서비스 등 실행 경계를 설계해야 하며, Java라는 이유만으로 AI 연동이 불가능한 것은 아닙니다.
- 두 프레임워크 모두 현재 정한 웹서비스 기능을 구현할 수 있습니다. 보안·확장성·처리 속도는 프레임워크 이름만으로 결정하지 않습니다.
- 추천 구조: FastAPI는 로그인·업로드·작업 접수·상태 및 결과 조회를 담당하고, 별도 Python 작업자가 OCR·분류·검색·설명 생성을 수행합니다. 작업 상태는 영속 저장하고, 재시도·취소·삭제를 작업자와 연동합니다.
- 무거운 분석을 API 요청 처리 안에서 실행하거나 FastAPI의 `BackgroundTasks`만으로 작업 수명 전체를 관리하는 방식은 추천하지 않습니다. 구체적인 작업 큐·저장소·인증 도구는 후속 선택 사항입니다.
- 참고: [FastAPI 기능](https://fastapi.tiangolo.com/features/), [FastAPI 백그라운드 작업](https://fastapi.tiangolo.com/tutorial/background-tasks/), [Spring Boot](https://spring.io/projects/spring-boot), [Spring Security OAuth2](https://docs.spring.io/spring-security/reference/servlet/oauth2/).

### 확정된 6개 기능의 세부 구현 제안

- 전체 요약과 점검 상태별 건수. 계약 조항 수와 점검 항목 수를 구분하고, 집계 단위를 정한 뒤 계산합니다.
- 점검 항목 목록 → 선택 항목의 상세 설명 → 계약서 해당 부분을 연결합니다. PC에서는 나란히, 모바일에서는 순차적으로 접근하는 구성을 제안합니다.
- 상세 정보: 계약 문장, 검토 이유, 근거 법령 원문·조문 번호·시행일·공식 출처 링크.
- 항목 상태 후보: 주의 필요 / 누락 의심 / 추가 확인 필요 / 기재 확인. 기재 확인은 적법성 확인을 의미하지 않습니다. 구체적인 판정 기준과 상태 우선순위는 미정입니다.
- 원문 위치를 보존해 해당 페이지로 이동하고 조항 영역을 강조합니다. 사용자 수정 텍스트와 원본의 연결을 유지하고, 정확한 위치를 연결하지 못하면 페이지 단위로 안내합니다.
- 각 항목에서 사용자에게 필요한 추가 정보를 제시합니다. 근거·적용 조건이 부족하면 판정을 보류합니다.

### 여력이 있을 때 추가할 후보

- 사업주에게 물어볼 질문 예시: 판정 결과와 연결한 제한된 템플릿부터 시작합니다.
- 사용자 답변을 통한 적용 조건 보완 및 관련 항목 재분석은 후속 버전 후보입니다. 첫 버전에는 별도 추가 질문 단계 없이 결과에서 정보 부족을 안내합니다.

### 후속 버전 후보

- PDF 리포트 내보내기, 공유 링크, 개인정보 자동 마스킹, 자유형 후속 질의응답.
- 저장·공유는 접근 권한·보관·삭제 정책과 함께 범위를 결정합니다.

### 기술적 전제와 표현상의 구분

- 현재 구현은 근로기준법 검색입니다. OCR, 조항 분리·분류, 누락 탐지, 적용 조건 판정, 설명 생성, 원본 강조 표시는 새로 구현해야 합니다.
- 검색된 조문이 존재하는지·인용 원문이 일치하는지 확인하는 것과, 해당 계약에 법령이 적용되는지 검증하는 것은 구분합니다. 현재 검색만으로 시안의 ‘근거 검증됨’을 표시하지 않습니다.
- ‘정상’, ‘적법’, 종합 안전 점수는 첫 버전에 권장하지 않습니다. 인식 실패·근거 부족·미지원 법령은 문제 없음으로 처리하지 않습니다.
- 시안에 포함된 연차·휴일 등은 적용 조건과 추가 법령의 필요성을 검토한 뒤 지원 범위를 정합니다. 검색 모델 점수를 위험 확률로 사용하지 않습니다.
- 원본 강조에는 페이지 번호·영역 좌표·텍스트 연결 정보가 필요합니다. 좌표를 반환하는 OCR/문서 추출 도구를 검토하되 특정 공급자는 아직 선택하지 않았습니다.
- 기술 참고: [Document Intelligence 레이아웃 문서](https://learn.microsoft.com/azure/ai-services/document-intelligence/prebuilt/layout?view=doc-intel-4.0.0).
