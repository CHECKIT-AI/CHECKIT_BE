# CheckIt 화면 동작 기준 핵심 API 명세

2026-10-21. 사용자가 선택한 ‘화면의 한 동작에 필요한 처리를 하나의 API로 묶기’ 원칙을 적용한 설계안입니다. 실행 코드는 아직 작성하지 않았습니다. 경로 접두사는 `/api`입니다. 인증은 [로그인 API 명세](auth-api-design.md), AI 호출은 [AI 함수 입출력](ai-interface-design.md)을 따릅니다.

## 1. API 구성 원칙

- 프론트엔드용 API는 화면에서 완료하려는 동작 단위로 제공합니다. 백엔드 내부는 검증·저장·AI 호출·결과 변환 함수로 나누며, 내부 함수마다 HTTP API를 만들지 않습니다.
- 업로드 전 사진 추가·삭제·정렬은 브라우저에서 처리합니다. 최종 선택한 파일과 순서를 ‘텍스트 추출하기’ 동작으로 한 번에 보냅니다.
- 추출·분석은 요청 연결을 유지하고 완료된 결과 또는 실패 이유를 반환합니다. 화면 종료 후 실행 지속·진행 상태 재조회는 첫 버전에 제공하지 않습니다. 저장된 완료 결과 조회와 명시적 분석 취소는 유지합니다.
- 인증·소유권·만료·파일 세대·텍스트 버전 검증은 통합하더라도 생략하지 않습니다. 내부 SQL 여러 건이 API 여러 개를 의미하지 않습니다.
- 외부 호출·파일 쓰기는 PostgreSQL 트랜잭션과 모두 원자적으로 묶을 수 없습니다. 입력 버전·중복 요청 방지·실패 복구를 설계합니다. 긴 AI 호출 동안 DB 행 잠금을 계속 유지하지 않습니다.

## 2. 전체 엔드포인트: 핵심 기능 10개

| 화면 동작 | 메서드·경로 | 요청 | 내부 처리와 응답 |
| --- | --- | --- | --- |
| 처음 텍스트 추출하기 | `POST /contracts` | multipart: contract_type, input_kind, request_id, files(확정 순서) | 검사 → 계약서 생성 → 원본·순서 저장 → 추출 → 텍스트 저장. 201: 계약서·파일·페이지·텍스트·확인 후보·만료 시각 |
| 오류 후 전체 파일 다시 올리기 | `PUT /contracts/{id}` | multipart: request_id, expected_file_generation_id, 전체 files | 기존 소유권·세대 확인 → 전체 파일 교체 → 순서 저장 → 재추출. 200: 새로운 파일 세대와 추출 텍스트 |
| 일시적 추출 오류 후 다시 시도 | `POST /contracts/{id}/extractions` | JSON: request_id, file_generation_id | 보관 중 원본으로 추출 재시도. 200: 추출 텍스트·버전·확인 후보 |
| 확인 후 분석 시작·수정 후 재분석 | `POST /contracts/{id}/analyses` | JSON: request_id, file_generation_id, base_revision_id, edited_blocks | 수정본 검증·저장 → 입력 확정 → 분석 → 결과 저장·교체. 200: 전체 결과·입력 버전 |
| 분석 취소 | `POST /contracts/{id}/cancel` | JSON: 대상 request_id | 취소 요청 검증·후속 처리 차단. 202: 취소 접수, 이미 취소 완료면 현재 상태 |
| 내 기록 목록 열기 | `GET /contracts` | 페이지네이션 파라미터 | 해당 회원·비회원의 기록 요약 목록. 200 |
| 기록·텍스트·결과 화면 열기 | `GET /contracts/{id}` | 경로 ID | 계약서·파일/페이지 정보·현재 편집 입력·저장 결과·만료 시각. 200 |
| 원본 파일 열기 | `GET /contracts/{id}/files/{file_id}` | 경로 ID | 접근 권한·만료·삭제 확인 후 파일 제공. 200 |
| 로그인 후 기존 결과 저장 | `POST /contracts/{id}/claim` | 회원 세션 + 비회원 접근 수단 | 소유권 전환·비회원 만료 해제. 200. 중복 기록 생성 없음 |
| 기록 삭제 | `DELETE /contracts/{id}` | 삭제 확인 후 요청 | 접근 차단·진행 작업 결과 게시 차단·파일 및 DB 정리. 202, 복구 불가 |

클릭 하나가 로그인 제공자 이동·이메일 수신·콜백처럼 여러 시점으로 나뉘는 경우까지 억지로 한 HTTP 요청에 넣지는 않습니다. claim은 이미 로그인한 후 저장을 누르는 동작에도 필요합니다. ‘로그인하고 기록 저장’ 흐름에서는 아래 인증 명세처럼 로그인 완료 처리 안에서 선택한 계약서 claim을 실행할 수 있습니다.

## 3. 업로드·추출 통합

- POST /contracts는 기존의 ‘계약서 생성’, ‘파일 업로드’, ‘페이지 순서 저장’, ‘최초 추출’을 통합합니다. 별도의 POST /contracts/{id}/files·PUT /contracts/{id}/pages/order는 제거합니다.
- PDF 한 파일 또는 사진 최대 10장, PDF 최대 10페이지, 파일당 20MB·원본 합계 100MB를 검사합니다. JPG/JPEG·PNG·HEIC를 지원합니다. MB 바이트 환산 기준은 미정입니다.
- 사진은 multipart 파일 배열 순서를 페이지 순서로 사용합니다. PDF는 실제 페이지 순서를 사용합니다. 처리 후 file_id·page_id를 반환합니다.
- 잠긴 PDF·손상·미지원 형식·용량 초과는 오류와 전체 재업로드 행동을 반환합니다. 추출 실패만으로 원본 불량이라고 단정하지 않습니다.
- 원본 저장은 성공했지만 OCR이 일시적으로 실패하면 오류 응답에도 본인 소유 contract_id·file_generation_id·복구 행동을 포함합니다. 새 계약서 생성부터 반복하지 않고 추출 재시도 API를 사용합니다.
- 재업로드는 일부 페이지 교체가 아닌 전체 파일 교체입니다. 같은 계약서의 first_uploaded_at·24시간 만료는 그대로 유지합니다. 교체 후 이전 파일의 결과는 새 파일의 결과처럼 표시하지 않습니다. 이전 파일·텍스트·결과 정리의 세부 순서는 구현 전 확정합니다.
- 첫 업로드 시간 기준 이벤트와 부분 업로드·실패 파일 정리 방식은 아직 미정입니다. 무효 업로드에 고아 파일이 남지 않도록 처리합니다.

## 4. 수정·확정·분석 통합

- 프론트엔드는 추출 응답을 받아 핵심 정보·불확실 부분을 우선 보여줍니다. 화면에서 수정하는 동안 로컬 편집 상태를 유지합니다. 별도 자동 저장 기능은 첫 버전에서 약속하지 않습니다.
- 분석 버튼을 누르면 바뀐 블록과 기반 버전을 함께 보냅니다. 수정하지 않았으면 edited_blocks는 빈 배열입니다.
- edited_blocks 원소는 block_id·text를 기본으로 합니다. 전체 텍스트 편집의 새 블록·삭제 표현 규격은 AI TextBlock과 맞춰 추가 구체화합니다. 좌표는 클라이언트가 임의로 만든 값을 그대로 신뢰하지 않습니다.
- 백엔드는 기반 텍스트·파일 세대 충돌 여부를 검사하고, content·offset을 재계산해 수정본을 저장·확정한 뒤 그 버전만 분석합니다. 전체 문서가 비거나 기존 파일과 연결할 수 없으면 입력 오류로 안내합니다.
- 분석에 사용할 확정 입력과 실행 기록은 짧은 DB 트랜잭션으로 저장합니다. AI 분석 중 DB 트랜잭션을 장시간 열어두지 않습니다.
- AI 단계에서 실패하면 이미 저장된 사용자 수정본은 유지해 재입력 부담을 줄입니다. 분석 성공 시에만 현재 결과를 최신 결과로 교체합니다. 재분석 실패·취소 시 기존 결과는 이전 입력 기준임을 구분해 유지합니다.
- 기존 text-revisions 저장 API·confirm API·GET text는 제거했습니다. 저장된 텍스트를 다시 읽을 때는 계약서 상세 GET을 사용합니다. 과거 텍스트·결과 비교 기능은 제공하지 않습니다.

## 5. 실행·취소·중복 요청

- request_id는 브라우저에서 요청 전에 생성한 UUID입니다. 같은 버튼의 네트워크 재전송은 같은 request_id, 사용자가 새로 실행하는 재시도는 새 ID를 사용합니다.
- 서버는 request_id를 소유자·동작·계약서·입력 내용과 결합해 검사합니다. 동일 ID의 다른 입력은 409로 거부합니다. ID만으로 권한을 인정하지 않습니다.
- 회원·비회원별 한 번에 한 건의 분석만 허용합니다. 경쟁 요청은 서버에서 제어하고 409를 반환합니다. 추출 중에도 같은 제한을 적용할지는 미정입니다.
- 분석 응답 전에도 계약서 ID와 request_id를 알고 있으므로 취소를 보낼 수 있습니다. 취소 접수와 완료는 구별합니다. 원래 분석 요청은 취소 확정 시 ANALYSIS_CANCELLED 오류로 종료하는 안이며 완료와 취소 경합은 원자적으로 제어합니다.
- 초기 업로드·추출은 응답 전 계약서 ID가 없을 수 있으므로 같은 취소 API로 추출 취소까지 지원한다고 가정하지 않습니다. 기존 확정 범위는 계약 내용 분석 취소입니다.
- 화면 이탈·네트워크 종료는 명시적 취소와 다릅니다. 감지 시 정리·실행 시간 제한·늦은 결과 저장·재요청 복구 정책은 후속 설계에서 정합니다. 서버 계산의 즉시 중단은 보장하지 않습니다.
- 서버 내부 작업 ID·상태는 중복 실행·취소·삭제 제어에 사용할 수 있습니다. 이를 위한 별도 프론트엔드 상태 조회 API는 만들지 않습니다.

## 6. 응답·오류

| 응답 구조 | 주요 내용 |
| --- | --- |
| 업로드·추출 성공 | contract_id, file_generation_id, files, pages, text(revision_id, content, blocks), review_candidates, expires_at |
| 계약서 상세 | 위 저장 정보 + current_result, 저장 결과 입력 버전과 최신 편집 입력이 다른지 표시 |
| 분석 성공 | contract_id, result_id, input_revision_id, summary, counts, items(설명·인용 근거·원본 위치), completed_at, expires_at |
| 공통 오류 | error.code, message, recovery_action, retryable. 필요 시 본인 contract_id·file_generation_id·저장된 revision_id |

HTTP 코드: 입력 정책 위반 400, 인증 없음 401, 비공개 대상 404, 버전·진행 작업 충돌 409, 용량 초과 413, 형식 미지원 415, 필드 오류 422, 일시적 외부 장애 503, 처리 제한 시간 초과 504를 후보로 합니다. 계약 내용의 주의 사항·추가 확인은 HTTP 실패가 아닌 정상 분석 결과입니다.

연결이 끊기면 서버 오류 응답 자체가 전달되지 않을 수 있으므로 프론트엔드는 네트워크 오류와 분석 오류를 구분해야 합니다. 임의의 진행률·근거 없는 적법 판정은 반환하지 않습니다.

## 7. 통합 전후

- 핵심 계약서 API: 15개 → 10개.
- 로그인·계정 API: 중복 claim 제외 9개. 기존 통합 후 12개에서 비밀번호 재설정 2개·회원 탈퇴 1개를 추가 제외했습니다.
- 전체 고유 HTTP API: 현재 19개(계약서·분석 10개 + 로그인·계정 9개). 2026-10-26 계정 연결은 제외했습니다. 제공자별 독립 계정을 사용하며 기존 API 내부 연결·재인증 분기를 제거하므로 경로 수는 동일합니다. 메서드+경로 패턴 기준이며 provider별 실제 URL·내부 Python 함수는 별도 집계하지 않습니다.
- 요청·응답 Pydantic 모델, 인증 상태·파일 세대·입력 버전 경합, AI 취소·시간 제한 등 실제 구현은 아직 수행하지 않았습니다.
