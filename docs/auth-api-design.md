# 로그인·계정 API 명세안

> 구현 갱신(2026-10-26): 이메일 가입·인증·로그인/로그아웃·CSRF·비회원 세션·기록 조회/귀속의 구현 범위와 설정은 [인증 구현 안내](auth-implementation.md)를 기준으로 확인합니다. 아래 소셜 로그인은 설계이며 아직 구현 전입니다.

2026-10-26 갱신. 기존에 확정된 로그인 요구사항을 구현 가능한 인터페이스로 구체화한 설계안입니다. 화면 동작 통합 원칙에 따라 공통 인증 처리를 같은 경로에서 처리합니다. 경로·필드·인증 수명은 설계안이며 아직 구현하지 않았습니다. 경로 접두사는 `/api`입니다.

## 0. 첫 버전 범위 변경

- 사용자 요청으로 비밀번호 재설정과 회원 탈퇴는 첫 버전에서 제외합니다. 해당 API·메일 발송은 구현 대상이 아닙니다. 개별 계약서 기록 삭제는 유지합니다.
- 이메일 로그인·로그아웃·카카오·구글 인증을 중심으로 범위를 줄입니다. 기존에 확정한 이메일 가입·인증은 별도 철회가 없어 우선 유지합니다.
- 2026-10-26 사용자 요청으로 계정 연결을 제외합니다. 이메일·카카오·구글은 각각 독립된 서비스 계정으로 가입·로그인하며 분석 기록도 따로 관리합니다. 이전 계정 연결 유지 결정을 대체합니다. 연결 및 이를 위한 재인증·병합 화면은 제공하지 않습니다.

## 1. 인증 방식

- 브라우저 웹서비스이므로 서버 저장 세션 + HttpOnly 쿠키 방식을 제안합니다. 세션 비밀값은 브라우저 쿠키, 검증용 해시는 PostgreSQL `auth_sessions`에 저장합니다. 응답 JSON이나 URL로 로그인 토큰을 제공하지 않습니다.
- 운영 HTTPS에서는 Secure, HttpOnly, SameSite=Lax 쿠키를 사용합니다. 로컬 HTTP의 Secure 예외는 개발 환경에서만 허용합니다. 프론트엔드·API를 같은 사이트로 배치하는 것을 기본안으로 하고, 실제 도메인 분리 시 쿠키·CORS 설정을 재검토합니다.
- 변경 요청에는 세션 쿠키 외에 CSRF 검증을 적용합니다. Origin 확인과 X-CSRF-Token 검증, 허용된 프론트엔드 origin만 CORS 허용하는 방향입니다.
- `GET /auth/csrf`는 현재 브라우저의 임시 컨텍스트·세션에 묶인 CSRF 토큰을 발급합니다. 로그인·가입 요청도 보호하며, OAuth 콜백은 일회성 state 검증으로 보호합니다.
- 초기 수명 제안: 회원 세션 7일(고정 만료), 가입 인증 링크 24시간, OAuth 진행 컨텍스트 10분. 전부 설정값이며 사용자 확정 정책은 아닙니다. 계약서의 24시간 보관과 별개입니다.
- 인증 성공 시 세션 ID·CSRF 컨텍스트를 교체합니다. 이메일 중복 가입·인증 재발송 요청에는 계정 존재를 드러내지 않는 동일한 응답을 사용하고 요청 제한을 둡니다. 제한 수치는 구현 전 정합니다.

## 2. 이메일 가입·로그인

| 메서드·경로 | 요청 | 응답·동작 |
| --- | --- | --- |
| `GET /auth/csrf` | 없음 | 200: `csrf_token`. 현재 브라우저 컨텍스트에 연결 |
| `POST /auth/signup` | `email`, `password` | 202: 공통 접수 메시지. 이메일 회원가입 인증 링크 생성 |
| `POST /auth/email-verification/resend` | `email` | 202: 동일한 공통 메시지. 재발송 시 이전 미사용 인증 토큰 폐기 제안 |
| `POST /auth/email-verification/confirm` | `token` | 200: 가입용 일회성 토큰 검증 후 이메일 가입 확정 |
| `POST /auth/login` | `email`, `password`, 선택적 claim_contract_id | 200: 해당 이메일 계정 세션·내 정보·새 CSRF, 선택한 비회원 기록 저장 결과 |
| `GET /auth/me` | 회원 세션 쿠키 | 200: 현재 계정의 사용자 ID·가입 제공자(provider). 미로그인 401 |
| `POST /auth/logout` | 회원 세션·CSRF | 204: 현재 세션 폐기·쿠키 제거 |

- 비밀번호는 요청으로만 받고 원문을 저장하거나 반환하지 않습니다. 길이 정책·해시 도구는 후속 기술 설정 대상입니다.
- 이메일 가입 인증 완료 후에는 자동 로그인하지 않고 로그인 화면으로 안내하는 것을 제안합니다. 인증 링크가 다른 브라우저에서 열려도 원래 비회원 계약서를 자동으로 연결하지 않습니다.
- 이메일 링크는 프론트엔드 확인 화면을 엽니다. 메일 보안 스캐너의 단순 GET 방문만으로 토큰을 소비하지 않고, 사용자가 확인한 뒤 위 POST를 호출합니다. 토큰 포함 페이지는 제3자 리소스·분석 스크립트와 URL 로그 노출을 피하고 토큰을 처리 후 주소에서 제거합니다.
- 잘못된 이메일·비밀번호는 공통 `INVALID_CREDENTIALS`. 올바른 비밀번호지만 가입 인증 전이면 `EMAIL_VERIFICATION_REQUIRED`를 반환하는 안입니다.
- 공개 `user` 응답은 ID·계정 상태·가입 제공자 정도만 포함하고 비밀번호 해시·제공자 토큰·내부 키는 반환하지 않습니다.

## 3. 카카오·구글 로그인

제공자는 `kakao` 또는 `google`만 허용합니다.

| 메서드·경로 | 요청 | 응답·동작 |
| --- | --- | --- |
| `POST /auth/oauth/{provider}/start` | return_path, 선택적 claim_contract_id, CSRF | 200: authorization_url. 로그인용 일회성 state 생성 |
| `GET /auth/oauth/{provider}/callback` | 제공자가 전달한 `code`, `state` 또는 오류 | 코드 교환·제공자 인증 후 세션 생성, 프론트엔드의 고정 완료 경로로 303 이동 |

- 프론트엔드는 authorization_url로 이동하고, callback의 code는 백엔드가 토큰으로 교환합니다. 제공자 토큰을 우리 서비스 로그인 세션 대신 쓰지 않습니다.
- state는 제공자·로그인 요청·브라우저·고정 콜백과 결합하고 일회성·만료 검증을 합니다. Google OIDC ID 토큰의 서명·issuer·audience·exp·nonce를 검증합니다. 카카오는 access token으로 공식 사용자 정보 API의 고유 ID를 확인하고 OIDC를 도입한다면 ID 토큰 검증도 추가합니다.
- return_path는 허용된 서비스 내부 상대 경로만 허용합니다. callback URL과 임의 외부 URL을 사용자 입력으로 교체하지 않습니다. 제공자별 PKCE 지원·설정은 실제 연동 단계에서 공식 문서와 SDK를 확인합니다.
- `(provider, provider_subject)`로 해당 제공자의 기존 서비스 계정을 찾습니다. 있으면 그 계정으로 로그인하고, 없으면 독립된 새 서비스 계정을 생성합니다.
- 같은 이메일의 EMAIL·다른 소셜 계정이 있어도 이번 제공자의 계정 생성·로그인은 허용하며 서로 연결하지 않습니다. 소셜 식별 기준은 이메일이 아닌 제공자 고유 ID입니다. 이메일 미제공 시에도 제공자 인증으로 계정을 식별합니다.
- 제공자 로그인을 거절하거나 실패한 경우 프론트엔드 완료 화면은 제한된 오류 코드만 조회·표시합니다. OAuth code·토큰을 이동 URL·일반 로그로 노출하지 않습니다.

## 4. 제공자별 독립 계정

- EMAIL·KAKAO·GOOGLE은 각자 다른 서비스 user_id를 사용합니다. 같은 사람이 같은 이메일로 사용하더라도 제공자가 다르면 분석 기록을 공유하지 않습니다.
- 이메일 가입 계정의 기록은 이메일 로그인으로, 카카오 계정 기록은 동일 카카오 계정 로그인으로, 구글 계정 기록은 동일 구글 계정 로그인으로만 확인합니다.
- 로그인 수단 연결·연결 해제·기존 계정 병합과 이를 위한 재인증은 제공하지 않습니다. 가입·로그인·OAuth 시작 요청에서 연결·재인증 목적을 받지 않습니다.
- 이전 LOGIN/LINK/REAUTH 및 LINK_EMAIL 분기는 폐기합니다. 전달되면 알 수 없는 필드·지원하지 않는 목적 오류로 처리하며 연결 로직을 실행하지 않습니다.
- auth_identities 구조를 유지한다면 user_id에 UNIQUE 제약을 둬 계정당 로그인 수단 하나를 표현하는 안입니다. `(provider, provider_subject)` 고유성은 유지합니다. 이메일 주소 전체에 제공자 구분 없는 전역 고유 제약을 두지 않습니다.
- 사용자 안내 예: ‘분석 기록은 가입한 로그인 방식별로 보관됩니다. 이전 기록은 당시 사용한 방식으로 로그인해주세요.’

## 5. 비회원 기록 저장

| 메서드·경로 | 요청 | 응답·동작 |
| --- | --- | --- |
| `POST /contracts/{id}/claim` | 회원 세션·CSRF + 해당 비회원 접근 수단 | 200: 공통 계정에 귀속된 계약서. 중복 요청은 중복 기록 생성 없이 응답 |

- ‘로그인하고 기록 저장’은 로그인 요청의 claim_contract_id로 선택한 계약서만 지정합니다. 이메일 로그인 성공 또는 소셜 로그인 콜백에서 비회원 접근 수단·만료를 다시 검증해 내부 claim 함수를 실행합니다. 프론트엔드가 별도 claim 요청을 연속 호출할 필요는 없습니다. 이미 로그인한 사용자의 별도 저장 동작에는 claim API를 사용합니다.
- 소셜 저장 의도는 브라우저 결합 서버 OAuth 컨텍스트에 보관합니다. 이메일 가입부터 진행한다면 원래 브라우저의 저장 의도를 유지하고 가입 인증 후 로그인 요청에 전달합니다. 이메일 토큰만으로 비회원 계약서 접근 권한을 부여하지 않습니다.
- 로그인 성공과 기록 저장 실패는 구분합니다. 만료·삭제·권한 문제로 저장하지 못해도 로그인 자체를 되돌리지 않고 claim_result에 실패 이유를 제공합니다. DB 상태상 기록이 귀속되지 않았는데 저장 성공이라고 표시하지 않습니다. 로그인만으로 모든 비회원 데이터를 자동 저장하지 않습니다.
- 이메일 가입·인증·로그인 사이에도 비회원 계약서의 첫 업로드 후 24시간 기한은 연장되지 않습니다. 인증 완료는 계정 저장 완료가 아닙니다.
- 회원 탈퇴 API는 첫 버전에서 제외했습니다. 개별 계약서 기록 삭제 API와 혼동하지 않습니다.

## 6. 공통 오류·보완 사항

응답 오류 형식은 핵심 API의 `error.code`, `message`, `recovery_action`, `retryable`을 따릅니다. 401은 인증 없음·잘못된 인증, 403은 CSRF 실패, 409는 기존 이메일 가입 등 계정 상태 충돌, 429는 요청 제한을 사용합니다. 인증 토큰 만료·사용·형식 오류는 비밀값을 포함하지 않는 공통 코드로 안내합니다.

세션·OAuth 진행 상태·CSRF 컨텍스트 저장 방법, 비밀번호 정책, 메일 발송 도구, 구체적인 수명은 구현 전 기술 설정으로 확정합니다. 메일 발송을 요청하는 API 명세를 작성한 것이며 실제 발송·제공자 앱 등록은 수행하지 않았습니다.

공식 참고: [카카오 로그인 REST API](https://developers.kakao.com/docs/ko/kakaologin/rest-api), [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect).

## 7. API 집계

이 문서의 현재 경로는 claim을 포함해 10개이며, 핵심 계약서 명세와 중복되는 claim 1개를 제외하면 로그인·계정 고유 경로는 9개입니다. 비밀번호 재설정 2개·탈퇴 1개를 제외했습니다. 계정 연결·재인증 분기는 제거했습니다. 원래 공통 API 내부 분기였으므로 경로 수는 바뀌지 않고 내부 구현 범위가 줄어듭니다. OAuth는 provider 패턴당 한 경로로 집계합니다. CSRF 초기화·소셜 콜백·이메일 링크 확인처럼 시점이 다른 필수 통신은 화면 동작 통합만을 위해 생략하지 않습니다.
