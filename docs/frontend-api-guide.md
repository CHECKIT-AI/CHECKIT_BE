# 프론트엔드용 API 명세서

> 구현 갱신(2026-10-26): 현재 사용 가능한 인증·조회·귀속 경로와 CSRF/쿠키 호출 순서는 [인증 구현 안내](auth-implementation.md)에 있습니다. 아래 전체 분석 흐름은 목표 설계이며 아직 모두 구현된 것은 아닙니다.

작성일: 2026-10-21. 계정 정책 갱신: 2026-10-26. 노션의 최신 업로드·로그인 명세를 기준으로, 프론트엔드 화면 연결에 필요한 호출만 정리한 안내서입니다. 서버 구현 완료를 의미하지 않으며, 상세 JSON 구조와 미정 정책은 연동 전에 확정해야 합니다. 아래 응답 필드 묶음은 현재 설계 계약입니다.

## 1. 먼저 연결할 핵심 흐름

2026-10-26 정리: 아래 버튼 이름은 실제 디자인에서 바꿀 수 있는 작업명입니다. 기존 API를 버튼·화면 진입에 매핑한 것이며 새 API를 추가하거나 기능을 합치는 변경은 아닙니다. ‘직접 호출 대상 18개’를 모두 버튼 18개로 만들지 않습니다.

### 1-1. 계약서 분석 화면의 버튼

| 화면 | 버튼·조작 | 호출할 API | 언제 호출하고 무엇을 표시하나 |
| --- | --- | --- | --- |
| 종류 선택 | ‘근로계약서’ 선택·‘다음’ | 없음 | 선택값과 화면 이동만 관리 |
| 파일 선택 | ‘PDF 선택’·‘사진 선택’ | 없음 | 기기의 파일/앨범 선택창을 열고 선택 목록을 브라우저에 보관 |
| 파일 선택 | 사진 추가·삭제·순서 이동 | 없음 | 브라우저의 최종 파일 목록·순서만 변경 |
| 파일 선택 | ‘텍스트 추출하기’ | `POST /contracts` (C1) | 최종 파일·순서를 한 번에 전송. 추출 완료까지 로딩 후 텍스트 확인 화면으로 이동 |
| 텍스트 확인 | 핵심 정보 확인·오타 수정·전체 텍스트 펼치기 | 없음 | 받은 텍스트를 화면에서 편집. 타이핑마다 저장하지 않음 |
| 텍스트 확인 | ‘확인 후 분석 시작’ | `POST /contracts/{id}/analyses` (C4) | 수정 블록도 함께 전송. 저장·확정·분석을 백엔드가 처리한 뒤 결과 화면 표시 |
| 분석 중 | ‘분석 취소’ → 확인창의 ‘취소하기’ | `POST /contracts/{id}/cancel` (C5) | 확인창을 여는 것만으로 호출하지 않음. 확인 후 원 분석 request_id를 전송하고 취소 처리 안내 |
| 분석 결과 | 점검 항목 선택·설명/근거 펼치기 | 없음 | 이미 받은 items·citations를 선택해 표시 |
| 분석 결과 | ‘텍스트 수정’ | 보통 없음 | 메모리에 있는 텍스트로 편집 화면 이동. 새로고침 등으로 입력이 없을 때만 상세 조회(C7) |
| 텍스트 재수정 | ‘다시 분석’ | `POST /contracts/{id}/analyses` (C4 재사용) | 새 수정 내용을 보내고 성공하면 최신 결과로 교체 |
| 분석 결과 | ‘원본 보기’·다른 원본 사진 선택 | `GET /contracts/{id}/files/{file_id}` (C8) | 아직 불러오지 않은 파일만 요청해 뷰어 표시. 같은 PDF의 페이지 이동은 이미 로드된 뷰어에서 처리 |
| 분석 결과 | ‘공식 법령 원문’ 링크 | 백엔드 API 없음 | 응답의 검증된 공식 출처 URL을 열기 |

**정상 분석 경로:** 파일 선택 → C1 → 화면에서 확인·수정 → C4 → 응답으로 결과 표시. 핵심 비즈니스 요청은 두 번이며 인증 초기화·원본 로딩을 포함한 전체 네트워크 요청 수가 두 번이라는 뜻은 아닙니다.

회원은 C4 성공 시 자동 저장됩니다. 별도 저장 버튼·claim 요청을 추가하지 않습니다. 결과를 막 받았을 때 C7을 다시 호출해 같은 결과를 재조회할 필요도 없습니다.

### 1-2. 오류 화면에서만 나타나는 버튼

| 오류 화면의 버튼 | 표시 조건 | 호출할 API | 프론트엔드 처리 |
| --- | --- | --- | --- |
| ‘전체 다시 업로드’ | 파일 손상·사진 읽기 불가·잠긴 PDF 등 | `PUT /contracts/{id}` (C2) | 새 파일 전체를 고르고 이 버튼으로 제출. PDF 잠금은 사용자가 기기에서 해제 |
| ‘텍스트 추출 다시 시도’ | 원본은 정상 저장됐고 OCR만 일시 실패 | `POST /contracts/{id}/extractions` (C3) | 보관된 원본 사용. 다시 파일을 고르게 하지 않음 |
| ‘분석 다시 시도’ | 계약 내용 분석의 일시적 실패 | `POST /contracts/{id}/analyses` (C4 재사용) | 저장된 수정본·기반 버전을 사용해 새 실행 요청 |

서버의 recovery_action·retryable과 현재 contract_id·파일 세대 존재 여부로 버튼을 고릅니다. 저장된 계약서 ID가 전혀 없는 업로드 실패는 C2를 호출할 수 없으므로 최초 제출(C1)로 다시 시도합니다. 오류 종류와 무관하게 모든 재시도 버튼을 동시에 표시하지 않습니다.

### 1-3. 기록 화면·저장·삭제 버튼

| 화면·동작 | 호출할 API | 처리 |
| --- | --- | --- |
| ‘점검 기록’ 탭으로 이동 | 화면 진입 시 `GET /contracts` (C6) | 목록 표시. 탭 클릭 핸들러와 진입 효과 양쪽에서 중복 호출하지 않음 |
| 목록에서 계약서 카드 선택 | 상세 진입 시 `GET /contracts/{id}` (C7) | 저장 결과·텍스트·파일 정보를 한 번에 표시 |
| 상세에서 ‘원본 보기’ | `GET /contracts/{id}/files/{file_id}` (C8 재사용) | 파일 바이트가 필요할 때 로드 |
| ‘삭제’ → 확인창의 ‘삭제하기’ | `DELETE /contracts/{id}` (C10) | 확인 후 한 번 요청. 성공하면 해당 기록을 화면에서 제거 |
| 비회원 결과의 ‘로그인하고 기록 저장’ | 이메일 로그인 A5 또는 소셜 시작 A8 | claim_contract_id로 이 계약서만 지정. 로그인 완료 처리에서 저장하므로 C9를 연속 중복 호출하지 않음 |
| 이미 로그인한 사용자가 보유 중인 비회원 결과의 ‘기록 저장’ | `POST /contracts/{id}/claim` (C9) | 이 예외 상황에서만 직접 호출. 기존 회원 분석의 자동 저장을 대신하는 버튼이 아님 |

### 1-4. 가입·로그인 화면의 버튼

| 화면 | 버튼 | 호출할 API | 다음 화면·결과 |
| --- | --- | --- | --- |
| 이메일 가입 | ‘가입하기’ | `POST /auth/signup` (A2) | 인증 메일 발송 안내. 가입 확정으로 표시하지 않음 |
| 이메일 인증 안내 | ‘인증 메일 다시 보내기’ | `POST /auth/email-verification/resend` (A3) | 재발송 접수 안내 |
| 메일 링크로 열린 확인 화면 | ‘이메일 인증 완료’ | `POST /auth/email-verification/confirm` (A4) | 토큰 검증 후 로그인 화면 안내 |
| 이메일 로그인 | ‘로그인’ | `POST /auth/login` (A5) | 세션·내 정보 갱신. 기록 저장 의도가 있으면 claim_result도 확인 |
| 로그인 | ‘카카오로 로그인’ | `POST /auth/oauth/kakao/start` (A8) | 응답 authorization_url로 브라우저 이동 |
| 로그인 | ‘구글로 로그인’ | `POST /auth/oauth/google/start` (A8 재사용) | 응답 authorization_url로 브라우저 이동 |
| 로그인 상태 메뉴 | ‘로그아웃’ | `POST /auth/logout` (A7) | 회원 상태를 비우고 비회원 화면으로 전환 |

두 소셜 버튼은 같은 provider 패턴 API를 재사용합니다. 계정 연결·비밀번호 재설정·회원 탈퇴 버튼은 만들지 않습니다. 이메일·카카오·구글 기록은 각각 별도 계정에 보관합니다.

### 1-5. 버튼이 아닌 공통 자동 호출·인증 이동

| 발생 시점 | 요청 또는 이동 | 프론트엔드 책임 |
| --- | --- | --- |
| 웹사이트 초기 진입·새로고침 시 | `GET /auth/me` (A6) | 로그인 상태·현재 계정 제공자 확인. 미로그인 401은 비회원 상태로 처리 |
| 첫 변경 요청 전 또는 CSRF 컨텍스트가 없을 때 | `GET /auth/csrf` (A1) | 공통 API 클라이언트에서 초기화·재사용. 각 버튼에서 따로 복제 구현하지 않음 |
| 소셜 인증 완료 시 | 제공자가 브라우저를 백엔드 callback으로 이동 | 프론트엔드가 callback을 fetch로 호출하지 않음. 서비스로 돌아온 뒤 필요하면 A6으로 현재 세션 확인 |
| 분석·추출 응답 성공 시 | 추가 상태·결과 조회 없음 | 받은 응답으로 화면 구성. 별도 진행 상태 폴링 없음 |

이 표는 호출 방식의 정리입니다. 공통 초기화 API를 하나로 합치거나 가입·재발송·재추출 경로를 통합하자는 이전 제안은 아직 적용하지 않았습니다. 총 HTTP 경로 19개·화면 코드 직접 호출 대상 18개는 유지하며, 각 화면은 자기 동작에 필요한 일부만 사용합니다.

분석 중에는 로딩 표시를 사용하고 화면을 유지합니다. 화면 종료 후 지속·재개 기능은 제공하지 않으며, 이미 저장된 완료 기록만 다시 열 수 있습니다. 이하 내용은 위 버튼 표의 C/A 참조 번호에 대한 상세 입력·응답·오류 규격입니다.

## 2. 모든 요청의 공통 규칙

| 항목 | 프론트엔드 처리 |
| --- | --- |
| Base URL | 환경 설정의 API 주소 + `/api`. 실제 호스트·포트는 미정 |
| 로그인 | 세션 쿠키 사용. fetch의 credentials 등 쿠키 전송을 맞추고 비밀번호·세션 비밀값을 localStorage에 저장하지 않음 |
| 요청 보호 | 초기 `GET /auth/csrf` 응답 토큰을 변경 요청의 `X-CSRF-Token`에 전달. 인증 성공 후 갱신된 토큰 사용 |
| 파일 전송 | FormData 사용. Content-Type의 multipart boundary는 브라우저가 생성하도록 두고 직접 JSON Content-Type을 지정하지 않음 |
| JSON 전송 | 파일 없는 요청은 application/json |
| ID | contract_id·file_id·revision_id·file_generation_id는 서버 응답값을 사용 |
| request_id | 실행 버튼을 누르기 전에 브라우저가 UUID 생성. 같은 요청의 재전송은 같은 ID, 새 실행은 새 ID |
| 시간 | API 시각을 한국 시간으로 표시. 서버가 준 expires_at을 기준으로 비회원 만료 안내 |
| 권한 | 회원·비회원 접근 확인은 서버 책임. 경로의 ID를 안다고 누구나 접근할 수 있는 구조가 아님 |

비회원 쿠키의 최초 발급 시점·전달 방식, 최종 환경별 CORS·CSRF 설정은 세부 인증 구현에서 확정합니다. 임의의 비회원 사용자 ID를 만들어 권한으로 사용하지 않습니다.

## 3. 계약서 화면 연결 API — 10개

| 번호 | 화면·사용자 동작 | 메서드·경로 | 보낼 데이터 | 응답으로 할 일 |
| --- | --- | --- | --- | --- |
| C1 | 처음 ‘텍스트 추출하기’ | `POST /contracts` | multipart: contract_type, input_kind, request_id, files | 201: 계약서 ID·파일 세대·페이지·추출 텍스트·확인 후보·만료 시각 저장, 텍스트 확인 화면 표시 |
| C2 | 문서 오류 후 ‘전체 다시 업로드’ | `PUT /contracts/{id}` | multipart: request_id, expected_file_generation_id, 전체 files | 200: 새 파일 세대·재추출 결과로 텍스트 확인 화면 갱신 |
| C3 | 일시적 OCR 오류 후 ‘다시 시도’ | `POST /contracts/{id}/extractions` | JSON: request_id, file_generation_id | 200: 저장된 원본의 재추출 결과 표시 |
| C4 | ‘확인 후 분석 시작’ 또는 수정 후 ‘다시 분석’ | `POST /contracts/{id}/analyses` | JSON: request_id, file_generation_id, base_revision_id, edited_blocks | 200: summary·items·근거·원본 위치로 리포트 표시 |
| C5 | ‘분석 취소’ 확인 | `POST /contracts/{id}/cancel` | JSON: 취소할 분석의 request_id | 202: ‘취소 처리 중’ 안내. 접수를 취소 완료로 단정하지 않음 |
| C6 | 기록 목록 화면 열기 | `GET /contracts` | 페이지네이션 파라미터 후보 | 200: 본인 기록 요약 목록 표시 |
| C7 | 저장된 기록 열기·텍스트 수정 화면 다시 열기 | `GET /contracts/{id}` | 경로 ID | 200: 계약서·현재 텍스트·저장 결과·파일 정보·만료 시각으로 화면 구성 |
| C8 | 계약서 원본·사진 열기 | `GET /contracts/{id}/files/{file_id}` | 경로 ID, 쿠키 인증 | 200: 파일 응답을 PDF/이미지 뷰어에 표시 |
| C9 | 로그인한 상태에서 비회원 결과 ‘기록 저장’ | `POST /contracts/{id}/claim` | 회원 쿠키·기존 비회원 접근 수단 | 200: 계정 저장 완료 표시. 아래 로그인 통합 저장 흐름이면 별도 호출 불필요 |
| C10 | 기록 ‘삭제’ 확인 | `DELETE /contracts/{id}` | 경로 ID, CSRF | 202: 즉시 목록·상세 접근에서 제거. 서버 파일 정리는 내부적으로 완료 |

### C1. 업로드·텍스트 추출

- contract_type은 현재 지원 계약서 코드(근로계약서 EMPLOYMENT 후보), input_kind는 PDF 또는 IMAGES입니다. 실제 선택 옵션 코드는 백엔드와 고정해야 합니다.
- files 배열에 최종 파일만 담고 사진의 배열 순서를 페이지 순서로 사용합니다. 순서를 바꿀 때마다 별도 API를 호출하지 않습니다.
- PDF 한 파일·최대 10페이지 또는 사진 최대 10장. PDF+사진 혼합 불가. 사진 JPG/JPEG·PNG·HEIC. 파일당 최대 20MB·전체 최대 100MB를 화면에서도 사전 안내합니다. 서버 검사가 최종 기준입니다.
- 원본을 저장한 뒤 OCR만 실패하면 오류 응답에 contract_id·file_generation_id가 포함될 수 있습니다. C1부터 다시 생성하지 말고 recovery_action에 따라 C2 또는 C3를 사용합니다.
- 처음 저장할 때 받은 first_uploaded_at을 기준으로 비회원 보관 기한은 24시간입니다. 재시도·추가 수정으로 연장되지 않습니다.

### C4. 수정본 저장·확정·분석

다음은 요청 구조 예시입니다. UUID 자리표시자는 실제 서버 응답 ID로 대체합니다.

```json
{
  "request_id": "<새 실행 UUID>",
  "file_generation_id": "<현재 파일 묶음 UUID>",
  "base_revision_id": "<화면에 읽어온 텍스트 버전 UUID>",
  "edited_blocks": [
    {"block_id": "<수정한 블록 ID>", "text": "<사용자가 수정한 문장>"}
  ]
}
```

- 수정하지 않았으면 edited_blocks는 빈 배열입니다. 수정본 저장 API·확정 API·분석 API를 순서대로 따로 호출하지 않습니다.
- 전체 텍스트 편집의 새 블록·삭제 표현은 아직 세부 규격이 미정입니다. 기존 블록 text 수정과 구분해 확정해야 합니다.
- 프론트엔드가 임의로 confirmed_at이나 원본 좌표를 만들어 확정하지 않습니다. 서버가 기반 버전 검증·문장 위치 재계산·입력 확정을 처리합니다.
- 결과는 summary, 상태별 counts, items를 표시합니다. 각 item에는 계약 문장·이유·추가 확인 정보·법령 인용·source_locations가 연결됩니다.
- 재분석 중 이전 결과를 최신 입력 결과로 표시하지 않습니다. 성공 시 교체하고 실패·취소 시 기존 결과를 유지합니다.

### C5. 취소

- 원 분석의 request_id를 유지해 별도 취소 요청으로 보냅니다. 단순히 원 요청의 브라우저 fetch를 abort한 것만으로 서버 취소를 보장하지 않습니다.
- 취소 확인 후 서버가 결과 게시를 막도록 하고, 원 분석 응답은 취소 확정 시 ANALYSIS_CANCELLED로 종료하는 설계안입니다. 확정 오류 상태 코드·원 요청 종료와 취소 응답의 경합은 구현 전 구체화합니다.
- C5는 계약 내용 분석 취소입니다. 최초 OCR 요청이 응답하기 전의 취소까지 같은 기능으로 제공하는 것은 아직 확정하지 않았습니다.

### C7·C8. 결과와 원본 연결

- 기록 상세에서 파일 ID·페이지 순서·원본 영역과 리포트를 한 번에 읽고, 실제 파일 바이트가 필요할 때 C8을 사용합니다. 파일 원문과 JSON 상세를 하나의 응답으로 합칠 필요는 없습니다.
- 사진은 해당 파일에 영역 강조, PDF는 source_page_number로 이동해 영역 강조합니다. 주어진 좌표 단위·정규화 규격을 따릅니다.
- 사용자 수정 문장과 원본이 다르거나 위치를 연결할 수 없으면 수정 표시·페이지 안내를 사용합니다. 임의의 원본 강조 영역을 만들지 않습니다.

## 4. 로그인·계정 화면에서 직접 호출하는 API — 8개

2026-10-26 변경: 계정 연결은 제외합니다. 이메일·카카오·구글은 각각 별도 계정이며 기록도 분리됩니다. 비밀번호 재설정·회원 탈퇴 제외는 유지합니다.

| 번호 | 화면·동작 | 메서드·경로 | 요청·응답 |
| --- | --- | --- | --- |
| A1 | 로그인·가입·비회원 동작 전 공통 초기화 | `GET /auth/csrf` | 200: 현재 브라우저 컨텍스트의 csrf_token. 같은 유효 컨텍스트에서는 재사용 |
| A2 | 이메일 회원가입 | `POST /auth/signup` | email·password. 202: 가입 인증 메일 발송 접수 |
| A3 | ‘인증 메일 다시 보내기’ | `POST /auth/email-verification/resend` | email. 202: 가입 인증 메일 재발송 접수 안내 |
| A4 | 메일 링크의 ‘인증 완료’ 확인 | `POST /auth/email-verification/confirm` | token. 200: 이메일 가입 인증 완료 |
| A5 | 이메일 로그인 | `POST /auth/login` | email·password, 선택적 claim_contract_id. 200: 해당 이메일 계정의 내 정보·쿠키·새 CSRF |
| A6 | 앱 초기 접속·새로고침 시 로그인 상태·계정 화면 조회 | `GET /auth/me` | 200: 현재 계정 ID·가입 제공자, 미로그인 401. 연결 목록은 제공하지 않음 |
| A7 | 로그아웃 | `POST /auth/logout` | 쿠키·CSRF. 204: 클라이언트의 회원 화면 상태 초기화 |
| A8 | 카카오·구글 로그인 | `POST /auth/oauth/{provider}/start` | 선택적 return_path·claim_contract_id. 200: authorization_url로 브라우저 이동 |

### 로그인 방식별 기록 안내

- 계정 연결 버튼·연결 목록·재인증 화면은 만들지 않습니다.
- 같은 이메일이라도 이메일·카카오·구글은 별도 계정입니다. 다른 방식으로 로그인해 기록이 비어 있어도 데이터가 삭제된 것으로 안내하지 않습니다.
- 이전 기록은 그때 사용한 로그인 방식과 동일한 제공자 계정으로 로그인해야 확인할 수 있습니다.
- 소셜 로그인은 처음이면 해당 제공자의 새 계정 생성, 이후에는 동일 제공자 고유 ID로 기존 계정 로그인입니다. 브라우저가 provider 이메일로 계정을 합치지 않습니다.

### ‘로그인하고 기록 저장’ 버튼

- 저장할 contract_id를 원래 브라우저에서 유지한 뒤 A5 또는 A8에 claim_contract_id로 보냅니다.
- 백엔드가 로그인 완료와 선택 기록의 계정 귀속을 함께 처리하므로, 성공 후 프론트엔드가 C9를 중복 호출할 필요는 없습니다.
- 이메일 신규 가입부터 진행하면 인증 후 로그인까지 저장 의도를 유지합니다. 이메일 인증 완료만으로 저장 성공이라고 표시하지 않습니다.
- 로그인 성공과 claim_result를 각각 확인합니다. 기록이 만료되어 저장에 실패해도 로그인은 성공할 수 있습니다. 로그인만으로 모든 비회원 계약서를 자동 저장하지 않습니다.
- 이메일 가입 인증 후 자동 로그인은 현재 명세에서 제공하지 않는 제안 상태입니다. 해당 흐름은 로그인 화면으로 안내합니다.

## 5. 프론트엔드에서 직접 API 호출 목록에 넣지 않는 것

| 항목 | 프론트엔드 역할 |
| --- | --- |
| 소셜 OAuth 콜백 | 카카오·구글 인증을 마친 브라우저가 백엔드 callback으로 이동합니다. 일반 화면 코드가 fetch로 callback을 직접 호출하지 않음 |
| OCR·조항 분류·RAG·설명 생성 함수 | 위 C1·C3·C4의 백엔드 내부 처리. AI 모델·Chroma에 브라우저가 직접 접근하지 않음 |
| 파일 검사·DB 저장·페이지 순서 저장 | 통합 API 내부 처리. 화면에서 개별 내부 API를 연속 호출하지 않음 |
| 별도 분석 상태 폴링 | 제외. 분석 요청의 응답을 기다림 |
| 비밀번호 재설정·회원 탈퇴 화면 | 첫 버전에서 제외 |

소셜 콜백은 필요한 서버 경로 한 개로 여전히 존재합니다. 전체 HTTP API 19개 중 화면 코드에서 호출할 수 있는 경로는 C1~C10과 A1~A8의 18개, 제공자 콜백은 1개입니다. 모든 사용자가 매번 18개를 호출하는 것이 아닙니다. AI 내부 함수는 이 숫자에 포함하지 않습니다.

## 6. 오류별 화면 행동

| 상황 | 화면 처리 |
| --- | --- |
| 파일 손상·잠긴 PDF·읽기 불가 | 이유 표시 → 전체 다시 업로드(C2). 잠금은 사용자 기기에서 해제 |
| OCR 일시적 장애 | 원본 유지 → 다시 추출(C3) |
| 분석 일시적 장애 | 저장된 수정본 유지 → 다시 분석(C4) |
| 입력 버전 충돌·분석 중복(409) | 중복 제출 차단·안내. 필요한 경우 상세(C7)를 다시 읽고 사용자 확인 후 실행 |
| 미로그인·세션 만료(401) | 해당 인증 요청이면 로그인 안내. 회원 전용 기능이 아닌 비회원 분석 자체를 무조건 막지 않음 |
| CSRF 실패(403) | 초기화 후 유효한 토큰 사용. 동일 요청을 무조건 반복하지 않음 |
| 비회원 24시간 만료 | 기록이 만료됐다고 안내. 삭제된 원본의 재사용·복원을 약속하지 않음 |
| 네트워크 종료·시간 초과 | 통신 실패와 서버 분석 오류를 구분. 기존 request_id를 유지하고 무조건 새 분석을 중복 실행하지 않음 |
| 정보 부족·근거 부족 | HTTP 오류 대신 리포트의 ‘추가 확인 필요’로 표시 |

공통 오류는 error.code·message·recovery_action·retryable을 기준으로 버튼을 선택합니다. 내부 경로·스택 트레이스를 사용자에게 표시하지 않습니다. GET /auth/me의 미로그인 401은 비회원 화면 진입 시 정상적으로 처리할 수 있어야 합니다.

## 7. 구현 순서와 남은 협의

1. 공통 API 클라이언트: 쿠키·CSRF·FormData·오류 처리.
2. C1 → 텍스트 확인·수정 → C4 → 결과 화면의 기본 흐름.
3. C5 취소, C2/C3 오류 복구, C6/C7/C8/C10 기록·원본 관리.
4. A2~A8 가입·로그인·로그아웃, C9 및 로그인 통합 기록 저장.

아직 확정해야 할 것: 실제 호스트·포트, 비회원 접근 수단 초기화, 페이지네이션 필드, 전체 텍스트의 새 블록·삭제 규격, JSON 응답의 최종 중첩 구조, 분석 시간 제한·취소 응답 경합·중복 요청 복구. 이 문서는 실제로 동작하는 서버 명세가 아닌 프론트엔드 협업용 설계입니다.
