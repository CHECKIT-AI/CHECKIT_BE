# 계약서 법적 누락·불리한 조항 탐지 기능 설계

2026-11-10 확정. 대상은 한국 근로계약서이며 근로자·입사 예정자의 관점에서 검토한다. 정규직·기간제·단시간 계약을 받을 수 있지만, 적용 조건이 확인되지 않으면 판단을 보류한다. 결과는 법 위반을 확정하지 않는다.

## 사용자 흐름과 개인정보 경계

1. 브라우저가 PDF 1개 또는 순서가 있는 JPG·PNG 사진을 연다. 텍스트 PDF는 브라우저에서 추출하고, 스캔 PDF·사진은 브라우저에서 한국어 OCR을 실행한다. 원본 파일·OCR 전 텍스트는 백엔드 또는 외부 OCR 서비스로 보내지 않는다.
2. 읽지 못한 페이지가 있으면 해당 페이지를 다시 올리고 OCR을 마칠 때까지 다음 단계로 가지 않는다. 일부 오탈자는 사용자가 원본을 보며 수정한다.
3. 사용자가 모든 페이지의 텍스트를 확인하고 직접 식별정보를 가린다. 임금·근로시간·날짜 등 판단에 필요한 값은 보존한다. 브라우저는 확인·마스킹 전 텍스트를 네트워크 요청, 로그, 분석 SDK, 영구 저장소에 넘기지 않는다.
4. Gemini에 마스킹된 계약 문구가 전송된다는 사실을 분석 버튼 전에 알린다. 사용자가 확인한 마스킹 텍스트와 페이지 번호만 백엔드에 보낸다. 원본 파일은 브라우저 화면을 닫으면 사라진다.
5. 분석은 서버에서 계속 실행된다. 사용자가 화면을 닫아도 회원 기록에서 진행 상태와 결과를 다시 조회한다. 기록에는 마스킹 텍스트와 결과만 남아 원본 보기·원본 이미지 좌표 강조는 제공하지 않는다.

자동 마스킹만으로 식별정보 제거를 보장할 수 없다. 전송 전 사용자 확인이 필수이며, 백엔드는 주민등록번호·휴대전화·이메일처럼 식별 가능한 형식을 추가로 거부한다. 이름·주소·계좌번호 등 모든 개인정보를 서버가 완벽하게 탐지할 수는 없다. 프론트엔드 구현과 실제 PDF·사진에서의 OCR 정확도·속도는 별도 검증 대상이다.

## 백엔드 계약

- `POST /api/contracts`: 쿠키 인증, Origin·CSRF 검증. `input_kind`는 `PDF` 또는 `IMAGES`, `pages`는 1~10개의 순서 있는 `{page,text}`이며 페이지 번호는 1부터 연속이다. `privacy_confirmed=true`, `gemini_notice_acknowledged=true`가 필요하다. 성공 시 `contract_id`, `revision_id`를 반환한다. 파일이나 원본 메타데이터는 받지 않는다.
- DB에는 회원 소유 `EMPLOYMENT` 계약, 파일 자산이 없는 입력 세대, `USER_EDITED`·확정된 마스킹 텍스트 revision을 저장한다. `text_revisions.blocks`는 `{page,start,end}`로 페이지 범위를 나타낸다. 기존 파일 기반 계약 조회 응답의 `files`·`pages`는 이 기록에서 빈 배열이며, `text.blocks`와 점검 항목의 `source_locations.page`로 페이지를 표시한다.
- `POST /api/analysis/contracts/{contract_id}/jobs`: 같은 회원의 현재 확정 revision을 분석한다. 매번 `privacy_confirmed=true`, `gemini_notice_acknowledged=true`가 필요하다. 이미 진행 중인 작업은 409. `GET .../jobs/{job_id}`와 `GET /api/contracts/{contract_id}`로 상태·결과를 조회한다. 서버 재시작으로 끊긴 작업은 FAILED가 되어 재요청한다.
- 모든 새 POST는 요청 크기 제한을 받는다. 명백한 직접 식별정보를 찾으면 `422 PERSONAL_DATA_DETECTED`로 저장·Gemini 호출을 막는다. 오류 응답에는 계약 문구를 넣지 않는다. 공개 응답에는 저장 키·내부 파일 경로를 넣지 않는다.

기존 DB 스키마·권한·RLS를 바꾸지 않는다. 원본 파일을 보관하지 않으므로 이 경로는 `file_assets`, `document_pages` 행을 만들지 않는다. 기존 파일 기반 계약 기록과 조회 API는 계속 읽을 수 있다. 기존 분석 시작 API에 필수 확인 필드가 추가되어 이전 호출자는 요청 본문을 갱신해야 한다.

## 분석과 결과

확정 텍스트를 페이지별 조항으로 나누고, 기존 분류·규칙 후보·법령 검색·Gemini 구조화 판단 흐름을 사용한다. 분류 라벨이나 검색 순위만으로 법 위반을 결정하지 않는다. 첫 규칙은 임금 구성·계산·지급, 근로시간, 휴일·연차, 근무 장소·업무의 명시 여부와 위약금, 2026 최저임금, 가산수당, 휴게시간을 검토한다. 계약상 불리함은 일방적 주요 조건 변경, 광범위한 손해 책임, 퇴사 후 취업 제한의 후보를 별도 `DISADVANTAGE` 유형으로 검토한다. 이 규칙은 후보 탐지이며 실제 계약서 평가로 정확도를 검증해야 한다.

점검 항목의 `rule_candidate.category`는 `MISSING`, `LEGAL_RISK`, `DISADVANTAGE` 중 하나다. 상태는 `MISSING_SUSPECTED`, `CAUTION`, `NEEDS_CONFIRMATION`, `PRESENT`를 사용한다. 계약서 근거 문구·페이지·설명·확인할 정보·실제 검색 결과에서 검증된 법령 인용 ID를 반환한다. 누락 후보는 문서 전체에서 검토하므로 원문 인용 위치가 없을 수 있다. 별도 취업규칙·부속합의서가 제출되지 않았거나 사업장 규모·근로형태·시행 시점이 불명확하면 추정하지 않는다.

법적 항목은 적용 연도와 인용 근거를 확인하지 못하면 `NEEDS_CONFIRMATION`으로 낮추고 법 위반 표현을 내보내지 않는다. 현재 검증된 수치 기준은 2026년 최저임금뿐이다. 다른 연도와 적용 범위를 확인할 자료가 없다면 수치 결론을 내지 않는다. `DISADVANTAGE`는 법적 판단과 별개로 근로자에게 불리할 수 있는 조건을 설명한다. 결과가 0건이어도 계약이 안전하거나 적법하다는 보장은 하지 않는다.

## 남은 연결과 검증

- 프론트엔드 저장소가 현재 작업 공간에 없어 브라우저 추출·한국어 OCR·페이지 재업로드·수정·마스킹·고지 UI는 아직 구현하지 못했다. 서버 API에 원본을 보내는 예전 프론트 설계는 이 문서로 대체한다.
- 실제 마스킹 계약서의 OCR→분석 종단간 정확도와 Gemini·RAG 실호출은 아직 검증하지 않았다. 사용자 데이터 또는 공유 DB를 이용한 통합 테스트는 별도 요청이 필요하다.
- 지원 계약 형태별 누락 기준과 법령 적용 조건, 검증된 법령 버전 범위는 법률 검토·평가 데이터를 통해 보강해야 한다.
